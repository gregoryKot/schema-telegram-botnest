# Заметка: почему `scripts/feature-parity-baseline.json` не на merge-драйвере

При добавлении гейта `check-feature-parity.mjs` (правило №3 CLAUDE.md) была
задача — свести новый бейслайн `scripts/feature-parity-baseline.json` тем же
merge-драйвером, что и остальные храповики (`.gitattributes` →
`scripts/merge-json-ratchet.mjs`, правило №13). Решение: **не сводить** —
файл остаётся на обычном текстовом слиянии git, строка в `.gitattributes` не
добавлена.

## Почему

`merge-json-ratchet.mjs` действительно не падает на объектных значениях —
структурно он рекурсивно обходит вложенные объекты. Но его СМЫСЛОВАЯ часть
(собственно «ratchet»: взять `min` двух чисел для метрик, где меньше лучше,
или `max`, где больше лучше) применяется только когда оба листа —
`typeof === 'number'`. Для всего остального у него один fallback:

```js
if (same(a, o)) return b;
if (same(b, o)) return a;
return bail(`несводимое расхождение в ${path}`);
```

То есть «взять сторону, которая не менялась относительно предка, иначе —
честный конфликт». Это разумное поведение само по себе, но это НЕ ratchet —
у `scripts/feature-parity-baseline.json` каждая запись это
`{ status: 'webapp-only'|'miniapp-only'|'nobody', reason: string, since: string }`.
Ни одно из полей не число, и ни для одного нет осмысленного «меньше/больше
лучше»: `reason` — свободный текст с человеческим объяснением, `since` —
хеш коммита, `status` — одно из трёх значений категории, не точка на шкале.
Взять «min» двух причин или «max» двух хешей коммитов бессмысленно.

Прогнать через `merge-json-ratchet.mjs` с флагом `min` (или `max` — для этого
файла разницы нет, ни один лист не число) технически возможно и не уронит
слияние с ошибкой — просто ни разу не сработает ветка, ради которой драйвер
писался. Это ровно тот случай, о котором предупреждает CLAUDE.md (правило
№13): «неоднозначное … драйвер не выдумывает — отдаёт обычный конфликт
человеку». Полагаться на побочное, не задокументированное для этого случая
поведение драйвера — то самое «удобное перетолкование», от которого
предостерегает правило №15 («гейт не замалчивают — его чинят»): вместо
настоящего ratchet-слияния получилась бы видимость его наличия.

## Что это значит на практике

- Два параллельных PR, добавившие РАЗНЫЕ ключи (разные роуты) в
  `feature-parity-baseline.json` — сольются как обычный JSON-текст без
  конфликта в БОЛЬШИНСТВЕ случаев, потому что реестр отсортирован (правило
  №13: «файлы-реестры, где порядок не значим, держим отсортированными») —
  вставки расходятся по файлу вместо общей точки в хвосте, как и у
  `dead-files-baseline.json`, который живёт по тому же принципу и тоже не
  требовал бы иного драйвера, если бы не был числовым по семантике причин
  (у него причины тоже строки — и он ПОД `merge=ratchet-min` в
  `.gitattributes`, но по факту работает через тот же fallback-по-предку, не
  через числовой ratchet; это осознанно оставлено как есть — не предмет этой
  заметки, трогать существующую строку не стал).
- Два PR, отредактировавших ОДНУ и ту же запись (например, оба поменяли
  `reason` для одного и того же роута) — дадут честный git-конфликт, который
  решает человек. Это ожидаемо и лучше, чем автоматическое слияние, которое
  тихо взяло бы одну из версий причины.

Если позже понадобится по-настоящему автоматическое слияние для этого файла
(например, при частых параллельных правках), это отдельная небольшая задача —
написать выделенный `merge-feature-parity-baseline.mjs` с явной семантикой
«новые ключи объединяются, изменённые общие ключи — конфликт» (то есть
формализовать именно то, что сейчас и так делает голый git на отсортированном
JSON) — но городить это ради гипотетической частоты правок сейчас
преждевременно.
