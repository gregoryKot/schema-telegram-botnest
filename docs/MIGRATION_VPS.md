# Переезд с Amvera на VPS

Прод жил на Amvera (один Docker-образ, Postgres рядом, деплой из `main`). Переезжаем
на свой VPS (Ubuntu 24.04, РФ, любой провайдер). Агент управляет сервером через
GitHub Actions: прямого SSH у него нет, ключ лежит в секретах репозитория.

**Репозиторий публичный, логи Actions видны всем.** Поэтому все операции печатают
только статусы, числа, sha коммитов и имена миграций. Env, логов приложения и
персональных данных в Actions нет и не будет; `set -x` в скриптах запрещён.

## Что где лежит

| Файл | Назначение |
|---|---|
| `deploy/vps/docker-compose.yml` | `db` (postgres:16, TLS), `app` (образ из ghcr), `caddy` (80/443) |
| `deploy/vps/docker-compose.transfer.yml` | override: публикует 5432 наружу, только на время переноса |
| `deploy/vps/Caddyfile` | все хосты приложения (список один, сверка с кодом: `src/infra/vps-caddyfile.spec.ts`) |
| `deploy/vps/bootstrap.sh` | первичная настройка чистого сервера, идемпотентна |
| `deploy/vps/ops.sh` | фиксированные операции: deploy, откат, перенос, статус |
| `deploy/vps/dc.sh` | единственная обёртка над `docker compose` на сервере |
| `deploy/transfer-db.sh` | перенос БД; запускается внутри контейнера на Amvera |
| `.github/workflows/deploy-vps.yml` | push в `main` → сборка → ghcr → сервер → здоровье → автооткат |
| `.github/workflows/vps.yml` | ручные операции (`op`) |

На сервере в `/opt/schemehappens`: `.env` (из секрета `PROD_ENV`), `db.env` (пароль БД,
создаёт bootstrap), `pg-tls/` (сертификат Postgres), `image`, `release`, `release.prev`
(образ и sha текущего и предыдущего релиза), флаги `HOLD_APP` и `TRANSFER_OPEN`.

Минимальный сервер: **2 vCPU, 4 ГБ RAM, 40+ ГБ NVMe, публичный IPv4**, Ubuntu 24.04.

## Что делает владелец

### 0. Скопировать ВСЕ env из панели Amvera в менеджер паролей

Раньше всего остального. `ENCRYPTION_KEY` шифрует свободный текст пользователей
(дневники, заметки, письма), `BACKUP_ENCRYPTION_KEY` шифрует бэкапы. Нигде, кроме env
Amvera, они не хранятся. Исчезнут вместе с аккаунтом Amvera, и перенесённая база
станет нечитаемой, а бэкапы в B2 не расшифровать. Сохранить значения, а не только
имена переменных.

### 1. Создать VPS

- Ubuntu 24.04, минимальная конфигурация выше, вход по SSH-ключу.
- Пару ключей для деплоя завести отдельно: `ssh-keygen -t ed25519 -f deploy_key -C github-actions`.
  Публичную часть положить в `~/.ssh/authorized_keys` пользователя `root`, приватную
  отдать в секрет (шаг 2).
- Записать IPv4 сервера.

### 2. Секреты репозитория (Settings → Secrets and variables → Actions)

| Секрет | Значение |
|---|---|
| `DEPLOY_HOST` | IPv4 (или имя) сервера |
| `DEPLOY_SSH_KEY` | приватный ключ целиком, включая строки `BEGIN`/`END` |
| `DEPLOY_KNOWN_HOSTS` | вывод `ssh-keyscan -t ed25519,rsa <IP>`, снятый из доверенной сети. Без него отпечаток берётся при каждом запуске и от подмены по дороге не защищает: в логе будет предупреждение |
| `PROD_ENV` | все env из Amvera, по строке `KEY=value` |

Формат `PROD_ENV`: как у `docker run --env-file`. Без кавычек, `$` и `#` внутри значений
остаются как есть. Строки `DATABASE_URL`, `RECOVER_CMD` и `TRANSFER_TARGET_URL`
сервер отбрасывает сам: адрес базы задаёт `docker-compose.yml`, а две другие запустили
бы перенос уже на новом сервере. Пока нет `DEPLOY_HOST`, `DEPLOY_SSH_KEY` или
`PROD_ENV`, обе воркфлоу зелёные и ничего не делают.

Сначала смержить PR с этими файлами в `main`: ручные воркфлоу видны в Actions только
из основной ветки, и запускаются они только с неё.

### 3. DNS: за сутки понизить TTL

На всех записях всех доменов TTL 300 секунд (кроме `MX`/`TXT`). Сами записи пока не
менять. Хосты (список один, `deploy/vps/Caddyfile`): `schemehappens.ru`, `schemalab.ru`,
`kotlarewski.gr`, `kotlarewski.ru` и `www.` каждого.

### 4. Amvera: подготовить перенос

Когда агент сообщит, что `op=transfer-open` выполнен, прочитать пароль БД на сервере:
`ssh root@<IP> cat /opt/schemehappens/db.env` (ключ от сервера есть у владельца; ни в
чат, ни в Actions пароль не попадает). Задать в env Amvera:

```
RECOVER_CMD=bash deploy/transfer-db.sh
TRANSFER_TARGET_URL=postgresql://postgres:<пароль>@<IP>:5432/schemehappens?sslmode=require
```

Перезапустить приложение. С этой секунды Amvera показывает страницу техработ: старый
хостинг запись не принимает, это граница простоя. `RECOVER_CMD` entrypoint запускает
после ожидания БД и до `migrate deploy`; скрипт делает дамп, заливает, сверяет числа и
**остаётся жить**, чтобы старый хостинг не запустил бота (два long-polling'а выбивали
бы друг друга). В логе Amvera ищите строки `[transfer]`:
`источник: миграций/пользователей = N/M`, `приёмник: ...`, `сверка сошлась`.

### 5. DNS: переключить A-записи

После `op=release-hold` и `status` с `"status":"ok"`: у регистратора A-записи всех
восьми хостов на IPv4 сервера, старые `AAAA` удалить (IPv6 на сервере не настроен).
Сертификаты Caddy выпустит сам, когда DNS дойдёт; не вышло за 10 минут, агент запускает
`op=restart-caddy`.

### 6. После переезда

- В env Amvera удалить `TRANSFER_TARGET_URL` (пароль БД нового сервера там больше не
  нужен). `RECOVER_CMD` оставить: пока он стоит, старая копия не стартует. Остановить
  приложение на Amvera не раньше, чем через неделю, когда новый сервер проверен.
- Проверить белые списки по IP у внешних сервисов (платёжка, почта, хранилище бэкапов),
  если они включены: исходящий адрес теперь другой.
- Дальше `RUNBOOKS.md`, `README`, `CLAUDE.md` описывают Amvera: см. «Что осталось
  открытым» в `docs/README.md`.

## Что делает агент (Actions → «Операции над VPS» → Run workflow, `op`)

Порядок строгий:

1. **`bootstrap`**: Docker и Compose из официального репозитория, ufw (22, 80, 443;
   5432 закрыт), автообновления безопасности, TLS-сертификат Postgres, пароль БД. На
   свежем сервере ставит `HOLD_APP`: приложение не стартует, пока не снят флаг. Иначе
   оно прогнало бы `migrate deploy` на пустой базе, и перенос отказал бы.
2. **Деплой** (Actions → «Деплой на VPS» → Run workflow, либо push в `main`): сборка
   образа, ghcr, `.env` из `PROD_ENV`, `docker compose up`. При `HOLD_APP` поднимаются
   только `db` и `caddy`, релиз записывается.
3. **`transfer-open`**: ставит `HOLD_APP`, открывает 5432 по TLS. Дальше шаг 4 владельца.
4. **`transfer-check`**: числа строк в `_prisma_migrations` и `"User"` и три последних
   имени миграций. Сверить с `[transfer]` из лога Amvera.
5. **`transfer-close`**: порт 5432 закрыт (проверяет, что опубликованного порта нет).
6. **`release-hold`**: снимает `HOLD_APP`, поднимает приложение (на нём пройдёт
   `migrate deploy` поверх перенесённой базы), ждёт `/health`.
7. **`status`**: релиз, флаги, `docker compose ps`, память, диск, ответ `/health`.
   Затем шаг 5 владельца (DNS), при необходимости **`restart-caddy`**.

Остальные операции: **`restart-app`**, **`rollback`** (на `release.prev`; после отката
`release.prev` стирается, второй откат невозможен).

## Деплой и автооткат

Каждый push в `main` собирает образ, публикует `ghcr.io/<repo>:<sha>` и `:latest`,
заходит на сервер и поднимает приложение. До 5 минут ждёт `/health` с
`"status":"ok"`. Не поднялось: возвращает `release.prev`, ждёт здоровья ещё раз, джоба
красная. В ghcr сервер входит токеном воркфлоу через stdin, во временном каталоге
настроек; он стирается сразу после `pull`. Диск: хранятся образы текущего и
предыдущего релиза.

Окно деплоя: приложение пересоздаётся, `migrate deploy` и запуск занимают десятки
секунд. Caddy ждёт до 20 секунд, дольше клиент видит 502.

## Если что-то пошло не так

- **Перенос отказал** (`ОТКАЗ: в приёмнике уже есть таблицы`). Приёмник не пуст: либо
  перенос уже был, либо приложение успело стартовать на пустой базе. Ничего не тронуто.
  Если база приёмника лишняя: на сервере `bash /opt/schemehappens/dc.sh exec db psql -U postgres -d
  schemehappens -c 'DROP SCHEMA public CASCADE; CREATE SCHEMA public'`, рестарт Amvera.
- **Перенос упал посередине.** Заливка идёт одной транзакцией, а обрыв дампа скрипт
  зачищает сам; причина в логе Amvera (только строки с ошибкой, без значений из таблиц).
- **Новый сервер не взлетел после переключения DNS.** Данные на Amvera целы (дамп
  только читает). Откат: DNS обратно, на Amvera убрать `RECOVER_CMD` и
  `TRANSFER_TARGET_URL`. Всё, что записали на новом сервере, потеряется.
- **Docker Hub или `download.docker.com` недоступны с сервера.** Bootstrap добавляет
  зеркало `mirror.gcr.io`; если Docker не ставится вовсе, поставить его вручную
  (Compose 2.30+) и повторить `bootstrap`.
- **Открыт порт 5432.** ufw порты Docker не фильтрует: пока `TRANSFER_OPEN` стоит,
  порт виден всему интернету, защищают пароль (48 hex-символов) и TLS (клиент требует
  `sslmode=require`). Не держать открытым дольше переноса.

## Чего здесь нет

Логов приложения в Actions: они лежат на сервере (`docker compose logs`, ротация
5 × 10 МБ) и будут доступны агенту через приватный репозиторий отдельным PR.
