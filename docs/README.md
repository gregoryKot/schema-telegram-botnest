## Что осталось открытым

Хвосты закрытых планов — то, что не сделано осознанно, а не забыто:

**Безопасность — аудит 2026-10** (реестр и детали:
[security/AUDIT_FINDINGS.md](security/AUDIT_FINDINGS.md), «Фаза 4»; решения по
хвостам — [SECURITY.md](SECURITY.md) §13):
- **Владельцу, срочно:** дамп боевой БД `scripts/railway_data.sql` всё ещё в
  публичной истории git (D-1). Перезапись отрепетирована 2026-10-04 на
  зеркале: `git filter-repo` трогает 3 коммита, деревья всех 172 веток
  остаются байт-в-байт прежними, файла не остаётся ни в одном коммите.
  Force-push всех веток агенту запрещён — выполнить руками (5 минут):
  `git clone --mirror <repo> m.git && cd m.git`, затем
  `git for-each-ref --format='%(refname)' refs/pull | xargs -n1 git update-ref -d`
  (ссылки PR на GitHub только для чтения), `git filter-repo --path
  scripts/railway_data.sql --invert-paths --force`, проверка
  `git log --all -- scripts/railway_data.sql` (пусто), `git remote add origin
  <repo> && git push --force --all origin`. После: запрос в поддержку GitHub на
  удаление висячих объектов (force-push их не удаляет), свежий клон у всех, кто
  работает с репозиторием, и подтверждение, что `JWT_SECRET`/`ENCRYPTION_KEY`
  той эпохи ротированы. Открытые PR dependabot переоткроются сами.
- **Владельцу:** бэкапы в B2 заработают, когда в Amvera заданы `B2_KEY_ID`,
  `B2_APP_KEY`, `B2_BUCKET`, `BACKUP_ENCRYPTION_KEY` (отдельный от ключа
  полей; см. `docs/ENV.md`) — планировщик, ретенция 90 дней и проба
  самопроверки «последний бэкап < 36 ч» уже в коде (D-2).
- **Владельцу, Amvera:** если `ALLOWED_ORIGINS` задан явно и содержит
  `kotlarewski.*` — убрать; проверка env теперь предупреждает об этом (F-2).
- Ссылка «написать в Telegram» (`tg://user?id=${partnerId}` в
  `shared/src/utils/therapistContact.ts`, `TodaySection.tsx`, `PartnerCard.tsx`)
  собирается из id связи, а у веб-партнёра (Google/VK/MAX/почта) это не
  Telegram-id — ссылка ведёт в никуда. Доказано чтением: id веб-аккаунта лежит
  в [1e18, 9e18). Нужно решение: прятать ссылку, если у партнёра нет Telegram.

**Хвосты решения по PII записи** (находка L3 аудита 2026-07-20, решение
владельца 2026-10-08 — ретенция 12 месяцев, `booking-retention.service.ts`;
принятый риск описан в [SECURITY.md](SECURITY.md) §13):
- **`ClientMeeting.clientKey` частично обнуляет обезличивание брони.** Крон
  затирает имя и контакт в `Booking`, но `clientKey` — это несолёный
  `sha256(нормализованный контакт)` и ключ строки (`prisma/schema.prisma`,
  `model ClientMeeting`), он остаётся. По утёкшему дампу `sha256` телефона
  перебирается, то есть на вопрос «записывался ли этот человек» база
  по-прежнему отвечает. Починка названа в D-9 и закрывает оба места разом:
  HMAC с серверным секретом вместо `sha256`. Нужна миграция (ключ строки) —
  поэтому не сделано в том же PR.
- **`Booking.meetingUrl` не затирается ретенцией.** Ссылка Zoom с `?pwd=` у
  брони годичной давности мёртвая, но формально это секрет, и он хранится
  бессрочно (зашифрованным, D-9). Решением владельца 2026-10-08 затираются
  ровно три поля — имя, контакт, текст запроса, — поэтому `meetingUrl`
  оставлен осознанно, а не забыт. Добавить в тот же `updateMany` — одна
  строка, но это расширение принятого решения, нужно «да» владельца.
- **Имя клиента уехало во внешние системы, и ретенция их не достаёт.**
  `booking-notify.service.ts:70` кладёт имя в `SUMMARY` события iCloud,
  `meeting.service.ts:154` — в тему комнаты Zoom (`Сессии — ${clientName}`).
  Крон затирает колонки в нашей БД, а копии в календаре владельца и в Zoom
  остаются: обезличивание получается неполным, и честнее это знать, чем
  считать класс закрытым. Чинится правкой события через CalDAV и
  переименованием комнаты — то есть исходящими вызовами площадок, у которых
  свои отказы и троттлинг (нужна проба самопроверки, правило №21). Объём
  работы несопоставим с самой ретенцией, поэтому отдельной задачей.
- **Два id человека остаются в чужих строках после удаления аккаунта:**
  `UserTask.assignedBy` (у задания живого клиента — id ушедшего психолога;
  удаление достаёт только задания офлайн-клиентов, `userId < 0`) и
  `TherapistRequest.reviewedBy` (кто рассмотрел заявку — владелец проекта).
  Оба помечены `ДОЛГ` в `PERSON_REF_COLUMNS`
  (`src/auth/table-registry.spec.ts`) — реестр теперь требует классификации
  каждой BigInt-колонки мимо `userId`, поэтому молча они больше не живут.
  Чинится переназначением на «удалённый пользователь» или обнулением; у
  `assignedBy` нужно решение, что показывать клиенту вместо имени психолога.


- **Фразы пула канала, добавленные через админку, не видит ни один гейт рода/голоса.** `check-gendered-forms`/`check-robot-phrases` читают только репозиторий, а `check-pool-sync` сверяет фолбэк `healthy-adult.data.ts` с миграциями — живой пул в БД (`HealthyAdultService.enabledTexts`, им же кормится «Фраза для себя» на сайте и в мини-аппе, `GET /api/healthy-phrase`) не проверяется ничем. Доказательство 2026-10-03: в пуле фраза «…Решение я уже принял…» (мужской род, реплика, которую пользователь примеряет к себе — по правилу «Род читателя» разводится обязательно; в git её нет). Кандидаты: проверка тех же паттернов при сохранении фразы в админке (`scripts/gendered-forms-patterns.mjs` → общий модуль) и/или блок в `/stats`. Саму фразу владелец правит в админке.
- **Каждый деплой — окно «Небольшие технические работы» на главной kotlarewski.gr, куда идёт реклама Директа** (владелец заметил 2026-10-03). Контейнер один: пока новый образ проходит `migrate deploy` и буст Nest, `deploy/front-server.mjs` отдаёт на любой путь и любой хост `deploy/maintenance.html` — со стороны рекламного клика это пустой сайт. Визитке для первого экрана бэкенд не нужен (статика `webapp/dist` + `/api/site-content` с фолбэком на `/gregory.jpg`). Кандидат: в окне старта front отдаёт для хоста визитки `webapp/dist/index.html` и статику с диска, а техработы — только API и продукту; форма записи в это окно честно говорит «не сохранилось» (`BookingErrorNote.tsx`). Окно пересборки образа (контейнера ещё нет) — уровень платформы, отсюда не закрывается.
- **Флак `webapp/src/sections/today/CaseEntryBlock.test.tsx`** (найден 2026-10-03 при полном прогоне vitest в webapp): тесты «Разобрать · ≈ 3 мин» и «Карта себя» падают по таймауту ~1 с на ленивой загрузке потока разбора, когда весь набор идёт параллельно; по отдельности файл зелёный (8/8). Найдено при сборке [RUNBOOKS.md](RUNBOOKS.md) (2026-10-08) — подробности в самом
документе, разделы «Чего не видит ни одна проба» и «Что проверить владельцу»:

То есть второй канал `notifyAdminWithFallback` может быть мёртв, и об этом не узнает ни проба, ни лог. Кандидат: проверять `res.ok` и класть результат в снимок, который видит `/stats`.

Пропустил DM — смотреть некуда, а именно так инцидент 2026-08-21 нашёл пользователь. Кандидат — перенести проверку в реестр проб самопроверки.

Кандидаты: отдавать фронту список доступных провайдеров и прятать кнопку, либо ловить отсутствие конфигурации в контроллере и вести на `/auth/error?reason=…`. Заодно поправить формулировку в реестре.
