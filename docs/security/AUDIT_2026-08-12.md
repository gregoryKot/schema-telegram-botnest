# Аудит безопасности и эффективности — 2026-08-12

Полный сквозной аудит бэкенда (NestJS), обоих фронтендов (webapp,
schema-miniapp), shared-пакета, инфраструктуры и БД. Читать вместе с
[SECURITY.md](../SECURITY.md) (модель угроз, инварианты) и
[AUDIT_FINDINGS.md](AUDIT_FINDINGS.md) (журнал прошлых находок).

**Метод.** Ручной разбор крон-путей auth/crypto/authz одной моделью + шесть
параллельных агентов по доменам: IDOR/ownership, фронт webapp, фронт miniapp,
SQL/инъекции, производительность/DoS, валидация/секреты/логи/rate-limit. Каждая
находка ниже проверена чтением кода (не грепом), с указанием `файл:строка` и
конкретным сценарием эксплуатации.

**Главное.** Найдена **одна критическая уязвимость** — неаутентифицированный
захват любого аккаунта через подделку `linkUserId` в неподписанном OAuth-`state`
(C1). Остальной контур крепкий: реальных IDOR не найдено, инъекции закрыты,
подписи/HMAC/JWT корректны, секреты не утекают, гварды на месте. Вторая ось —
эффективность: несколько путей концентрируют нагрузку и не масштабируются
(полуночный планировщик, горячий путь трекера, отсутствующий индекс `Rating.date`).

## 🔴 C1 — Захват любого аккаунта через подделку `linkUserId` (Critical)

**Файлы:** `src/auth/auth-flow.service.ts:158` (`linkUserIdFromState`, сток),
`:182-202` (`oauthRedirect`, источник `state`), `:204-243` (`oauthCallback`),
`src/auth/auth-oauth.controller.ts:42-51` (google callback, без гварда);
параллельный вектор — `tg_link_user`-кука в `src/auth/auth-telegram.controller.ts:77-85`.

**Суть.** `state` в OAuth-редиректе — это **не подписанный** `base64url(JSON)`,
хотя комментарий утверждает «подписанный»:

```ts
// oauthRedirect (:188)
const state = Buffer.from(
  JSON.stringify({ nonce: randomBytes(16)..., linkUserId: req.webUser?.userId?.toString() ?? null }),
).toString('base64url');
// linkUserIdFromState (:158) — читает linkUserId из того же state без проверки подписи
```

Единственная защита на колбэке — double-submit-кука (`savedState === state`) +
`requireCsrf`. Оба сценария защищают лишь от **кросс-сайт**-атакующего, который
не может прочитать/поставить куку. Атакующий, который делает запрос **своим
HTTP-клиентом** (curl/Burp), ставит `oauth_state`-куку и query-параметр `state`
в одно и то же подделанное значение — проверка проходит. `linkUserId` становится
полностью подконтролен атакующему. `GoogleProvider.exchangeCode(code)`
(`google.provider.ts:47`) — **stateless**, к `state` никак не привязан.

**Эксплойт (Google, без аутентификации):**
1. Атакующий заводит одноразовый Google-аккаунт (в приложении не привязан).
2. Авторизует наше приложение своим Google → получает валидный `code` на наш
   `redirect_uri`. (Первый браузерный заход в колбэк отбивается проверкой
   `state` **до** обмена кода — код остаётся непогашенным, атакующий читает его
   из редиректа.)
3. `GET /api/auth/google/callback?code=<свой code>&state=<base64url({linkUserId:"<ЖЕРТВА>"})>`
   с заголовком `Cookie: oauth_state=<тот же state>`.
4. Сервер: `savedState === state` ✓ → `exchangeCode` → личность **атакующего** →
   `linkProviderToUser(<ЖЕРТВА>, 'google', <sub атакующего>)` (`auth.service.ts:322`)
   — sub свободен → **привязывает Google атакующего к аккаунту жертвы**, `{ok:true}`
   → `issueTokens(<ЖЕРТВА>)` (`auth-flow.service.ts:100`). В ответе — refresh-кука
   и access-токен **жертвы**. Ветка линковки **явно пропускает 2FA** (:98).

`userId == telegramId` для телеграм-юзеров (перечислим/добываем), поэтому
`<ЖЕРТВА>` тривиально известен. Итог: **полный захват аккаунта + обход 2FA +
постоянный бэкдор** (Google атакующего теперь логинит в аккаунт жертвы).

**Векторы:** Google ✅ уязвим; Telegram-OIDC ✅ уязвим (PKCE-verifier в куке,
атакующий ставит свою); Telegram-widget ✅ уязвим через `tg_link_user`-куку
(`auth-telegram.controller.ts:77`, значение берётся сырым `BigInt(cookie)`).
**VK защищён** — PKCE-verifier хранится на сервере в мапе, ключ = `state`
(`vk.provider.ts:52,91`), поддельный `state` не имеет verifier'а → отказ.

**Почему не поймали гейты.** `injection.invariants.spec.ts` проверяет
eval/Function/RawUnsafe/whitelist — это auth-логика, не инъекция.
`auth.service.security.spec.ts` пинит `algorithms:['HS256']`, но `state`
вообще не JWT.

**Фикс.** Подписать носитель `linkUserId` (тем же `JWT_SECRET`, как
`buildMergeToken`/`verifyMergeToken`): `state` и `tg_link_user`-кука становятся
подписанными токенами (`kind:'oauth_state'`, TTL 10 мин, iss/aud). Проверять
подпись в `linkUserIdFromState`; при провале — `linkUserId = null`
(анонимный вход, не захват). Double-submit `savedState === state` остаётся.
VK-путь не ломается (verifier по-прежнему по строке state).

**Статус:** 🔧 исправлено в этом PR (см. изменения auth-flow / oauth /
telegram-контроллеров + тесты).

## 🟠 H1 — 2FA обходится на путях, минующих `signInOrLinkOrMerge` (High)

**Файлы:** `src/auth/auth-account.controller.ts:110-136`
(`POST /api/auth/telegram/webapp`), `src/auth/auth-max.controller.ts:36-76`
(`POST /api/auth/max/webapp`), `src/auth/auth.service.ts:160-214`
(`consumeEmailToken`, вызывается из `email/callback`, `auth-account.controller.ts:54`).

TOTP-гейт живёт **только** в `AuthFlowService.signInOrLinkOrMerge`
(`auth-flow.service.ts:77`). Три первичных пути входа зовут `issueTokens()`
напрямую, минуя `totp.isEnabled`. Это **задокументировано** как известный BUG в
`test/auth-flows.e2e-spec.ts:252-261`, но не починено («production src is out of
scope for this task»).

**Эксплойт (email — самый чистый).** Юзер с привязанным `email` и включённым
TOTP. Атакующий с доступом к почте: `POST /api/auth/email/link {email: жертва}`
→ читает magic-link из почты → `email/callback` → полная сессия **без второго
фактора**, хотя тот же аккаунт требует TOTP при входе через Google. 2FA
становится не сильнее слабейшего включённого метода — атакующий выбирает путь.

Пути telegram/max-webapp менее остры (initData доказывает владение аккаунтом
мессенджера), но всё равно: юзер, включивший TOTP на вебе, при следующем
открытии мини-аппа проходит без кода.

**Фикс (email — закрыт).** `consumeEmailToken` вынесен в `EmailTokenService`
(`src/auth/email-token.service.ts`) и при `login` + включённом TOTP отдаёт не
сессию, а TOTP-challenge; `email/callback` редиректит на существующую
`/auth/2fa?token=` (фронт не меняется). Привязка (`link_email_auth`) не гейтится
— это подтверждение из уже своей почты. `recovery/confirm` пропускает 2FA
**осознанно** (`auth-2fa.controller.ts:160`) — recovery-grade фактор.

**telegram/max-webapp — принято by design.** Это обмен `initData` на сессию
ТОЛЬКО изнутри мини-аппа, а мини-апп параллельно ходит и по stateless-пути
`x-telegram-init-data` (per-request, `TelegramAuthGuard`), который TOTP-гейтить
нельзя в принципе — это не сессия, а доказательство владения аккаунтом. Гейт
только на bootstrap при открытом per-request пути — театр: атакующий со свежей
initData просто ходит по второму пути. Владение мессенджер-аккаунтом здесь и есть
фактор.

**Статус:** ✅ email закрыт (этот PR); telegram/max-webapp — accepted by design.

## 🟠 H2 — Yandex Webvisor пишет клинический текст третьей стороне (High)

**Файлы:** `webapp/src/components/CookieBanner.tsx:23-29` (`webvisor: true`),
`webapp/src/App.tsx:8-14,71-80` (`MetrikaTracker` на всех роутах), сток —
`webapp/src/.../LetterEx.tsx:71` (рендер письма себе), и аналогично
safe-place / дневник / YSQ.

Метрика инициализируется с **Webvisor** (полная запись сессии/DOM) и монтируется
в `Root`, оборачивающем **авторизованное** приложение `schemehappens.ru`. Эти
экраны рендерят сохранённый клинический текст обратно в DOM (письма, дневники,
нарративы о травме/суициде). Webvisor снимает уже отрендеренные текст-ноды
(маскирование инпутов на них не действует) → контент уходит на `mc.yandex.ru`.
Технических меток исключения (`ym-disable`/`ym-hide`) нет нигде; риск не отражён
в SECURITY.md §11.

Смягчение: выключено по умолчанию, требует явного согласия «Принять все».
**Фикс:** `webvisor: false` в `loadMetrika` (`CookieBanner.tsx`). Это SPA —
Метрика инициализируется один раз и живёт на всех экранах; погейтить запись по
маршруту нельзя (рекордер уже запущен к переходу на клинический экран), а
классы-исключения на каждом узле хрупки (ровно та дыра, что породила находку).
Полное отключение записи сессий убирает утечку целиком; агрегатная аналитика
(визиты/клики) остаётся. Из копии баннера убрано «(с записью сессий)».

**Статус:** ✅ закрыто.

## 🟠 H3 — Полуночный планировщик: O(юзеры × ~15 запросов) серийно в 00:00 UTC (High, perf)

**Файлы:** `src/telegram/telegram.schedule.service.ts:235-248`
(`@Cron('0 0 * * *')`), `src/bot/account.service.ts:152`
(`getAllUsersWithSettings`, без `take`), `src/notification/notification.planner.service.ts:41`
(`planDay`).

```ts
const users = await this.accountService.getAllUsersWithSettings(); // ВСЕ, без пагинации
for (const user of users) { await this.plannerService.planDay(user); } // серийно
```

Каждый `planDay` фанится в ~10-20 round-trip'ов (cadence.evaluate + гарантированный
`user.update`, затем insight/weeklyStats/bestDay — полный скан `Rating` — или
`scheduleReminder` с `Promise.all` из `getConsecutiveDays`+`getWeeklyStats`+
`getHistoryRatings`, каждый заново тянет tz и сканит рейтинги). Всё это — один
плотный серийный цикл в один момент 00:00 UTC на весь юзербейз, независимо от
таймзоны юзера. 1k юзеров ≈ 15k серийных запросов; 10k ≈ 150k, часть — полные
per-user сканы + запись. На одном маленьком Postgres это забивает пул/CPU/IO на
всё окно. Худший scheduled-job: нагрузка сконцентрирована, а не размазана.

**Фикс:** tz из уже загруженного `user` прокинут в аналитику планировщика —
методам `BotAnalyticsService` (getDaysSinceLastFill/getWeeklyStats/
getConsecutiveDays/getHistoryRatings/getLowStreakNeeds/getFillDaysInLast) добавлен
опциональный `tzArg?`, а `NotificationPlannerService` передаёт `user.notifyTimezone`
вместо ~4 повторных `SELECT notifyTimezone` на юзера в полуночном пике. Обратно
совместимо (без аргумента — старый путь). Более крупное «размазать по локальной
полуночи / уменьшить тяжёлые сканы Rating» — отдельный рефактор движка
уведомлений, высокий риск регрессии, оставлен на этап масштабирования.

**Статус:** ✅ проброс tz закрыт; спред/сокращение сканов — deferred (future-scale).

## 🟠 H4 — Горячий путь трекера: повторные `userTimezone()` + двойные полные сканы истории (High, perf)

**Файлы:** `src/bot/bot.analytics.service.ts` — `userTimezone()` (`:20`) зовётся
независимо внутри `getConsecutiveDays`/`getWeeklyStats`/`getHistoryRatings`/
`getFillDaysInLast`/`getActiveDates`/`getDaysSinceLastFill` (3-4 одинаковых
`SELECT notifyTimezone` на запрос); `getBestDayOfWeek` (`:428`) и
`getWorstDayOfWeek` (`:677`) — каждый `rating.findMany({where:{userId}})` без
`take`/`select`, а `/api/insights` (`tracker.controller.ts:131`) зовёт **оба** →
история грузится дважды. `getActiveDates` тянет полные appActivity + все три
дневника; крутится на `/streak`, `/insights`, `/export`, `/achievements` и после
каждого сохранения рейтинга.

Это самый частый авторизованный путь (каждое открытие мини-аппа). Cost =
(длина истории юзера) × (повторные сканы) × (конкурентность). Многолетний юзер
тянет тысячи строк по нескольку раз за экран.

**Фикс:** best/worst-day слиты в один `getDayOfWeekExtremes` (один
`rating.findMany` с `select` вместо двух полных сканов), `/api/insights` зовёт
его один раз — самый частый двойной скан на горячем пути убран, дубль-код
методов удалён (jscpd упал). Сквозной проброс `tz` через planDay сделан в H3
(там он и концентрировал нагрузку); точечный микро-опт остальных `userTimezone`
на текущем масштабе — низкая выгода/риск, оставлен на потом.

**Статус:** ✅ двойной скан best/worst закрыт; проброс tz — в H3.

## 🟡 M1 — `startParam` авто-джойнит пару/терапию без подтверждения (Medium)

**Файлы:** `schema-miniapp/src/App.tsx:365-387`; бэк —
`src/bot/pairs.service.ts:65-83`, `src/therapy/therapy-relations.service.ts:43-59`.

На маунте `startParam` (подконтролен атакующему через `?startapp=…`) превращается
напрямую в приватные state-changing вызовы **без диалога подтверждения**:

```ts
if (startParam?.startsWith('pair_'))    api.joinPair(startParam.replace('pair_',''))
if (startParam?.startsWith('therapy_')) api.joinTherapy(startParam.replace('therapy_',''))
```

`joinPair` → пара `active` → каждый партнёр видит рейтинги+7-дн историю другого;
создание инвайта пары **без ролевого барьера**. `joinAsClient` → делает жертву
**клиентом** создателя инвайта, терапевт читает клинику (заметки, YSQ, дневники);
создание инвайта гейтится ролью `THERAPIST`. Атакующий шлёт `t.me/<bot>/app?startapp=pair_<code>`
под видом «открой приложение» — на загрузке авто-джойн, жертва не видит «Присоединиться? Поделиться данными?».

**Фикс:** явный экран-подтверждение перед сетевым вызовом `joinPair`/`joinTherapy`.

**Статус:** ✅ закрыто (этот PR). startParam `pair_`/`therapy_` больше не джойнит
на маунте — открывается `JoinConfirmSheet` (мини-апп), сетевой вызов только
после явного «Присоединиться». Закрытие любым способом (крестик/бэкдроп/
хост-назад/«не сейчас») = отказ, `api.join*` не зовётся (fail-closed). Экран
честно называет объём расшаривания (партнёр видит индекс дня и неделю — прежняя
копия это занижала; терапевт — клинику по выбору в настройках). Тексты в обеих
формах ты/вы, объём вынесен «в контексте» (правило онбординга). Тесты:
`JoinConfirmSheet.test.tsx` (fail-closed, джойн по подтверждению, видимая ошибка,
форма «вы») + `App.dataload.role.test.tsx` (маунт открывает согласие, не джойнит).
Веб-двойника нет — на сайте присоединение только ручным вводом кода в настройках.

## 🟡 M2 — Нет индекса `Rating.date`; `/stats` seq-сканит + 4 ретеншен-`GROUP BY` без фильтра (Medium, perf)

**Файлы:** `prisma/schema.prisma` (Rating: только `@@unique([userId,date,needId])`
+ `@@index([userId,date])`); `src/bot/bot.analytics.service.ts:560-634`.

Все запросы `getAdminStats` фильтруют по **голому `date`** и не могут использовать
userId-ведущий индекс: `COUNT(DISTINCT userId) WHERE date=today`, `groupBy(needId)
where date>=d7`, churn `date>=d30 lt d7`, и **четыре ретеншен-запроса** (`:597-619`)
`SELECT userId FROM Rating GROUP BY userId HAVING COUNT(DISTINCT date)>=N` — **без
фильтра по дате вообще**, полный `GROUP BY` по всей таблице ×4. Rating растёт
~5 строк/юзер/день, так что стоимость `/stats` растёт с размером таблицы. Только
для админа/редко, но многосекундный full-scan конкурирует с живым трафиком.

**Фикс:** добавлен `@@index([date])` на `Rating` (миграция
`20260813060000_rating_date_index`, `CREATE INDEX "Rating_date_idx"`, проверяется
джобой `migrations`) — `/stats`-запросы по голому `date` больше не seq-сканят
растущую таблицу. Rollup 4 ретеншен-`GROUP BY` (сейчас без фильтра по дате) —

## 🟡 M4 — Алерт-канал заливается варьируемым не-цифровым текстом через неавториз. синк (Medium, I-4)

**Файлы:** `src/logger/alert.logger.ts:22-25` (нормализация ключа),
сток — `src/auth/auth-telegram.controller.ts:229-236`.

`AlertLogger.alert` строит 60с-dedup-ключ, заменяя только цифры (`\d+`) и
uuid/hex — **буквы не нормализуются**. Любой `logger.error()`, чей **первый
аргумент** содержит варьируемый атакующим не-цифровой текст, обходит троттлинг:
один DM админу (Telegram + email-fallback) на каждый ключ.

Конкретный синк: `telegram/widget-redirect` (`:150`, GET, **без аутентификации и
без `@Throttle`**) логирует `query keys=${JSON.stringify(Object.keys(query))}`.

ключи → флуд чата и исходящей почты. Именно тот вред, ради которого троттлинг и
делали (замьюченный чат = потерянные реальные алерты).

**Фикс:** нормализовать ключ агрессивнее (или бить по call-site, как `AlertBudget`
в `SecurityLogService`); держать текст из запроса вне алертируемого первого
аргумента (паттерн уже применён в `client-errors.controller.ts`).

**Статус:** ✅ закрыто (этот PR). Два уровня: (1) **сток** — в `widget-redirect`
первый аргумент `.error()` теперь постоянен (`telegram widget-redirect error
(детали в логах)`), имена query-параметров и текст ошибки уехали ВТОРЫМ
аргументом (только в лог, не в DM — инвариант H0/H6). (2) **системный backstop** —
`AlertLogger` получил общий бюджет `AlertBudget(60_000, 15)` поверх
пер-контентного ключа: варьируемый буквами текст из ЛЮБОГО стока (текущего или
будущего — те же `prisma-exception.filter` с `req.url` в ключе) больше не заливает
чат сверх 15/мин суммарно, а реальная авария из нескольких подсистем (< 15)

## 🟡 M5 — `trust proxy` не задан, но код доверяет `x-forwarded-proto` (Medium, infra)

**Файлы:** `src/main.ts:41` (`req.headers['x-forwarded-proto']`); `trust proxy`
не задан нигде (греп пуст).

Код полагается на `x-forwarded-proto` (доказательство L7-прокси), но `trust proxy`
не выставлен → Express игнорирует `X-Forwarded-For`, и `req.ip`/`req.ips` отражают
**прокси**, а не клиента. Все IP-ключевые механизмы деградируют:
`throttler.guard.ts:29,58` (неавториз. бакеты и суффикс `|ip:` на `uid|ip` —
весь смысл правила №5 — схлопываются в один глобальный бакет),
`WebSession.ipAddress` (`auth.service.ts:527`), IP в `SecurityLogService`,
`initdata-alert.ts:51` (`take(ip)`) — аудит-логи и троттлинг suspicious-initData
теряют гранулярность.

Величина зависит от топологии Amvera (если реальный IP приходит только в XFF —
воздействие полное; если Amvera отдаёт клиентский socket-IP — меньше). Но
факт кода — доверять XFP, не доверяя XFF — верифицирован.

**Фикс:** `app.set('trust proxy', 1)` (или верное число хопов) и брать `req.ip`
из XFF — **либо** подтвердить, что Amvera передаёт реальный socket-IP, и убрать
зависимость от XFP.

**Статус:** ✅ закрыто (этот PR): `app.set('trust proxy', 1)` в `main.ts` (Express
типизирован как `NestExpressApplication`). Доверяем ровно одному хопу — Amvera;
не `true`, иначе клиент подделает XFF. Теперь `req.ip`/`req.ips` берут адрес из
X-Forwarded-For, и IP-механизмы (бакеты троттлинга правила №5,
`WebSession.ipAddress`, IP в аудит-логах и `initdata-alert`) снова гранулярны.
Консистентно с уже существующим доверием к `x-forwarded-proto` ниже по файлу.

## Проверено и признано крепким (явные негативы)

Строгий аудит обязан показать покрытие, а не только находки.

- **IDOR/ownership:** все выборки/удаления скоупятся `userId` из гварда
  (`uid(req)`), нигде не из body/param; `deleteMany`/`updateMany` с
  `{id,userId}`. Терапевт→клиент — `assertRelation` первой строкой у всех
  аксессоров; виртуальные клиенты (`-id`) обрабатываются, не обходятся.
  `addClientManually` (реальные юзеры) **отключён** (`therapy-connection.controller.ts:113`,
  ForbiddenException). Capability-токены (`/by-token/:token`) — `randomUUID`,
  строгий allowlist без PII. Merge/pairing — target из гварда, подписанный
  merge-токен.
- **Инъекции:** ни один пользовательский ввод не доходит до raw SQL; идентификаторы
  в `merge.service.ts` — через whitelist `KNOWN_TABLES`/`KNOWN_COLS` + `ident()`;
  единственный `$executeRawUnsafe` — литерал `VACUUM ANALYZE "User"`. Нет
  operator-injection в `where`/`orderBy`/`select` (`ValidationPipe({whitelist})` +
  явные `clean`-объекты). Прото-поллюшн: весь `JSON.parse` читает известные ключи
  или пересобирает из allow-list, без spread/assign. Нет eval/Function/child_process.
- **Подписи:** Telegram initData (`SKIP_AUTH` жёстко off в prod), MAX initData
  (HMAC + `timingSafeEqual` + ровно один hash + expiry после подписи), JWT
  (iss/aud/type/`algorithms:['HS256']` пинятся) — корректны. Crypto: AES-256-GCM,
  `authTagLength:16`, multi-key rotation, warn на провал GCM.
- **CSRF/куки:** каждый ambient-cookie state-changing эндпоинт зовёт `requireCsrf`;
  куки `httpOnly+secure`, `SameSite=strict` (осознанный `none` только для
  MAX-iframe, серверная метка + CSRF-заголовок).
- **Секреты/логи:** нет секретов в git/коде/тестах; всё через `ConfigService`.
  `SecurityLogService.redact` вырезает token/secret/initdata; нет интерполяции
  `decrypt()`/`initData`/`req.body` в логи. Энтропия: `crypto.randomBytes`/
  `randomInt`, нет `Math.random` в security-путях.
- **Admin-гейт:** `admin-key.util` — constant-time, пустой ключ всегда отказывает.
  Robokassa webhook — MD5 подпись, `safeEqualHex`, идемпотентный CAS.
- **Фронты:** access-токен только в памяти; фрагмент чистится `replaceState` до
  await; нет открытых редиректов; единственный `dangerouslySetInnerHTML` — через
  DOMPurify allowlist; кризисная детекция на всех free-text (гейт
  `crisis-path.invariants.spec.ts`); `max-bridge.js` — якорный `/(^|[#&])WebAppData=/`
  (фикс 2026-08-08). Host-detection не путает мессенджеры.
- **Ресурсы:** все server-side `fetch` с `AbortSignal.timeout`; тело 256KB;
  большинство in-memory-стора (AlertThrottle/AlertBudget/pendingPairCodes/
  SlotAttempts) — с cap/прунингом; DTO-массивы в основном ограничены; прочие
  кроны — с `take`/индексами.
