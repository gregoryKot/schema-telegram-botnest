### F-2-02 · `qs` 6.14.2 — DoS через `qs.stringify` ✅ Закрыто

- **Источник:** `npm audit` + `osv-scanner` (GHSA-q8mj-m7cp-5q26)
- **Severity:** CVSS 6.3 Medium (upstream) → **Low** в нашем контексте
- **Описание:** `qs.stringify` падает с `TypeError` на null/undefined в
  comma-format массивах при `encodeValuesOnly`.
- **Контекст:** `qs` приходит транзитивно через Express (для `qs.parse`
  на `req.query`). Мы **не вызываем `qs.stringify`** напрямую. Уязвимый путь
  не достигается из нашего кода.
- **Действие:** `npm audit fix` → `qs` 6.14.2 → 6.15.2.
- **Верификация:** `npm audit` после — 0 vulnerabilities.

### F-2-03 · `valibot` 1.0.0-beta.14 — ReDoS в `EMOJI_REGEX` ❌ Не эксплуатируется

- **Источник:** `osv-scanner` (GHSA-vqpr-j7v3-hqw9 / CVE-2025-66020)
- **Severity:** CVSS 7.5 High (upstream) → **Info** в нашем контексте
- **Описание:** `EMOJI_REGEX` валидатора `v.emoji()` имеет catastrophic
  backtracking. Короткая (~99 символов) крафтовая строка из regional indicators
  отжирает CPU на минуты. Если бы наш auth-путь вызывал `v.emoji()` на
  юзер-полях, был бы устойчивый DoS на каждый initData.
- **Контекст:** транзитивная зависимость через
  `@telegram-apps/init-data-node` → `@telegram-apps/transformers` → `valibot`.
  Grep `v\.emoji|emoji\(\)|emoji:` в `node_modules/@telegram-apps/*` — **0
  совпадений**. Уязвимая функция в нашей интеграции не вызывается.
- **Статус:** ❌ Отклонено как не-эксплуатируемое; зависимость уязвима, но путь
  не достигается. Следить за апстримом — когда `@telegram-apps/transformers`
  обновится, vuln уйдёт сама. Альтернатива (если в проекте появится прямой
  `v.emoji()` где-либо): npm `overrides` для пиннинга `valibot >= 1.2.0`.

### F-2-04 · GCM без явного `authTagLength` в `crypto.ts` ✅ Закрыто

- **Источник:** `semgrep` rule `javascript.node-crypto.security.gcm-no-tag-length`
- **Severity:** **Low** (hardening / defense in depth)
- **Файл:** `src/utils/crypto.ts:48` (`createDecipheriv`) — и симметрично
  `:27` (`createCipheriv`).
- **Описание:** Node `createCipheriv`/`createDecipheriv` с GCM по умолчанию
  принимают любую длину auth-тэга из {4, 8, 12, 13, 14, 15, 16} байт. Короткий
  тэг = ослабленная аутентификация (4-байт — 2³² форджей вместо 2¹²⁸).
- **Контекст:** в нашем коде tag всегда `buf.subarray(12, 28)` = 16 байт
  (а `buf.length < 29` отсекается раньше). Эксплуатации сейчас нет, но явный
  опшен закрепляет инвариант — будущий рефактор не сможет случайно его сломать.
- **Действие:** добавил `{ authTagLength: 16 }` в оба вызова.
- **Верификация:** `tsc` чист; round-trip encrypt/decrypt с новым опшеном
  работает; ciphertext бинарно-идентичен — обратная совместимость с уже
  зашифрованными в БД данными подтверждена (decrypt без опшена читает тот же
  ciphertext).

## Фаза 4 — Аудит данных клиента и психолога (2026-10-03)

План — [AUDIT_PLAN_2026-10.md](AUDIT_PLAN_2026-10.md). Шесть срезов, каждый —
таблица «вход → защита → вердикт» по всем элементам. Главный итог: инварианты
§2/§3 плейбука (каждый маршрут под гвардом, каждая выборка по `userId` из

plaintext в очереди уведомлений. Нумерация: буква среза + номер.

### A. Психолог ↔ клиент

#### A-1 · Текст задания психолога лежал открытым в `ScheduledNotification.payload` ✅ Закрыто
- **Severity:** Medium. `UserTask.text` шифруется, а та же строка уезжала
  в payload уведомления `task_assigned` открытым текстом; реестр шифрования
  называл колонку «без свободного текста» (ложная запись, правило №15).
- **Фикс:** свободные поля payload шифруются при записи и расшифровываются
  при чтении (`src/notification/`), запись реестра переведена в `enc`.

#### A-2 · `DELETE /api/therapy/relation` от психолога стирал всю практику ✅ Закрыто
- **Severity:** Medium. `disconnect` удалял `OR [{therapistId},{clientId}]`:
  один вызов от психолога — исчезали все клиенты, виртуальные клиенты и
  приглашения, заметки о виртуальных становились недостижимы навсегда.
- **Фикс:** `disconnect` удаляет только связь, где вызывающий — клиент;
  психолог убирает клиентов по одному через `DELETE clients/:id`.

#### A-3 · Клиент мог быть подключён к двум психологам, видя одного ✅ Закрыто
- **Severity:** Medium (прозрачность доступа). `joinAsClient` отвергал лишь
  повтор того же психолога; `GET relation` отдавал первого. Второй психолог
  читал трекер и карточки невидимо.
- **Фикс:** `join` отказывает, пока есть активная связь с другим психологом
  (`reason: 'already_connected'`).

#### A-4 · Виртуальная ветка `assertRelation` без `clientId: null` ✅ Закрыто
- **Severity:** Low. `-relId` связи с РЕАЛЬНЫМ клиентом проходил как
  виртуальный — теневой бакет, который `getClients` не показывает. Утечки
  между психологами нет (везде `therapistId`), но два механизма проверки
  (`assertRelation` и копия в `getTasksForClient`) могли разойтись.
- **Фикс:** `clientId: null` во всех виртуальных ветках; `getTasksForClient`
  ходит через `assertHasClient`.

#### A-5 · Код приглашения психолога: без срока, неатомарный захват ✅ Закрыто
- **Severity:** Low. Энтропия 48 бит достаточна; но код живёт вечно, каждое

#### A-6 · Слабые DTO `session-info` и `tasks` ✅ Закрыто

#### A-7 · `tasks/all` показывал шифротекст алиаса; дубль проверки связи ✅ Закрыто

### B. Аутентификация и сессии

#### B-1 · Восстановление refresh-цепочки обходило детекцию кражи 🔧 В работе
- **Severity:** High. Исход `recover` (ответ ротации не доехал) выдавал новую
  пару предъявителю УЖЕ ротированного токена, если наследник не отозван.
  Вор и жертва, чередуясь, продвигают цепочку бесконечно: каждый раз
  наследник «цел», `theft` не наступает, алерта нет. Заявление в шапке
  `refresh-rotation.ts` («как только двое используют цепочку — отзыв») было
  неверным.
- **Фикс:** счётчик восстановлений в семье (`recoveredAt` на строке,
  рождённой восстановлением): третье восстановление за сутки — кража, семья
  отзывается, алерт. Легитимная гонка (повтор + поздний ответ) даёт максимум два.

#### B-2 · Login-CSRF через `?link_token=` в query ✅ Закрыто
- **Severity:** High. `OptionalJwtGuard` принимал link-токен из query. Атакующий
  чеканит токен для СВОЕГО аккаунта и отправляет жертву на
  `/api/auth/google?link_token=…`: Google жертвы привязывается к аккаунту
  атакующего (или чеканится merge-токен жертва→атакующий).
- **Фикс:** только httpOnly-cookie; query-fallback удалён.

#### B-3 · Анонимное подтверждение слияния ✅ Закрыто
- **Severity:** High (в паре с B-2). `confirmMerge` принимал анонима с
  merge-токеном. Теперь вызывающий обязан доказать, что он `target`: Bearer
  или refresh-кука живой сессии `target`.

#### B-4 · Привязка почты отдавала сессию заявителя тому, кто кликнул ✅ Закрыто
- **Severity:** High. `link-to-account` слал письмо «Войти», а переход по
  ссылке привязывал адрес к аккаунту заявителя И ставил его refresh-куку в
  браузер получателя. Атакующий «привязывает» чужой адрес: жертва кликает —
  её почта теперь ведёт в аккаунт атакующего, а дневник пишется туда же.
- **Фикс:** отдельное письмо о привязке; погашение `link_email_auth` требует
  живой сессии того же `userId`; токены не выдаются.

#### B-5 · Слияние обходило TOTP исходного аккаунта ✅ Закрыто
- **Severity:** High. Компрометация только первого фактора жертвы (Google) +
  конфликт при привязке → merge-токен → данные жертвы уезжают в аккаунт
  атакующего, её `totpSecret` отбрасывается.
- **Фикс:** merge-токен несёт `sourceTotp`; подтверждение требует код TOTP
  источника (`403 source_totp_required`, ввод кода на `/account/merge`).
  Путь привязки через билет (`TicketLinkService.approve`) — см. открытое B-12.

#### B-6 · Коды TOTP без лимита; счётчик `2fa/challenge` в памяти инстанса ✅ Закрыто
- **Severity:** Medium. `2fa/disable` при 200/мин подбирается за сутки.
- **Фикс:** `@Throttle` 5/мин, 20/ч + `@PersistentThrottle` на всех
  проверяющих код маршрутах; событие `totp_failed` в журнал безопасности.

#### B-7 · `JWT_SECRET` без требования к длине ✅ Закрыто

#### B-8 · Виджет Telegram принимался 24 часа ✅ Закрыто — окно 15 минут.

#### B-9 · Неатомарное погашение токенов восстановления/подтверждения почты ✅ Закрыто — CAS.

#### B-12 · TOTP не спрашивается на входе через initData (Telegram/MAX) ⚠️ Открыто (решение владельца)
- Человек включил TOTP на сайте; тот, кто контролирует его Telegram, открывает
  мини-апп и получает всё плюс 30-дневную веб-сессию через `telegram/webapp`.
  Это продуктовое решение «мессенджер = доверенное устройство», но оно не
  задокументировано и не показано на экране настройки 2FA. Варианты: челлендж
  TOTP раз на устройство, либо честная подпись на экране 2FA. Сюда же —
  одобрение привязки через билет в мессенджере без второго фактора источника.

#### B-13 · Удаление аккаунта без повторной аутентификации ⚠️ Открыто (решение владельца)
- 15-минутного access-токена достаточно для необратимого удаления всех
