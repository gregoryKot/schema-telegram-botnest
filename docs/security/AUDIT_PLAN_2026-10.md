# Аудит безопасности 2026-10: данные клиента и данные психолога

План ретеста и расширения прошлых аудитов (2026-05, 2026-07, 2026-08). Прошлые
проходы закрыли классы и зафиксировали их трипваерами (`src/security/*.spec.ts`,
[../SECURITY.md](../SECURITY.md) §15). Этот проход отвечает на другой вопрос:
**что в контуре появилось с тех пор и ни одним трипваером не накрыто** — и
доказывает ответ кодом, а не ощущением.

Связанные документы: модель угроз — [THREAT_MODEL.md](THREAT_MODEL.md);
реестр находок — [AUDIT_FINDINGS.md](AUDIT_FINDINGS.md) (этот аудит пишет туда
раздел «Фаза 4 — 2026-10»); плейбук — [../SECURITY.md](../SECURITY.md).

## От кого (из модели угроз, уточнено)

- **T2 рядовой пользователь** — читает чужое по `id` (IDOR), ломает инварианты
  тела запроса (mass assignment), злоупотребляет логикой (пары, экспорт).
- **T3 психолог** — читает клиентов ДРУГОГО психолога, читает бывшего клиента
  после разрыва, читает клиента, не давшего согласия, повышает роль.
- **T4 клиент** — читает заметки психолога о себе или о других, цепляется к
  психологу без приглашения, завершает чужие задания.
- **T6 доступ к устройству** — кэш в `localStorage`, Service Worker,
  сессия на общем компьютере, смена аккаунта на одном устройстве.
- **T5 хост/бэкап** — дамп + env вместе, незашифрованные бэкапы, логи с
  текстом.

## Срезы проверки (шесть направлений, параллельно)

Каждый срез = таблица «вход → защита → вердикт» по КАЖДОМУ элементу, а не
выборочно. Находка без строки кода и сценария атаки — не находка.

| Срез | Что проверяем | Чем доказываем |
|------|---------------|----------------|
| A. Психолог ↔ клиент | каждый маршрут `src/therapy/**`, `/api/therapy/**`, экспорт: `assertRelation` первой строкой, статус связи, виртуальные клиенты (отрицательный id), noteId/taskId скоуплен по психологу, роль — только сервером, заявка одобряется только `ADMIN_ID`, удаление аккаунта клиента чистит записи психолога о нём | таблица маршрутов + e2e на ownership по каждому маршруту без теста |
| B. Аутентификация | JWT (alg/iss/aud/тип), refresh (ротация, кража, logout), initData TG/MAX (HMAC, свежесть, replay), виджет, OAuth (state, PKCE, open redirect, привязка по email), merge, TOTP на всех путях входа, login-ticket/magic-link (энтропия, TTL, одноразовость, перебор), троттлинг по верифицированной идентичности | таблица путей входа + негативные спеки |
| C. IDOR и деньги | каждый `findUnique/update/delete` по `id` без `userId`; `updateMany` с проигнорированным count; mass assignment через `@Body()`; пары; экспорт; админ-контроллеры (как доказан админ); Robokassa (подпись, сумма, идемпотентность, by-token без PII); бронь (P-5 — время против правил доступности) | таблица маршрутов + e2e |
| D. Данные в покое и стирание | каждая String/Json-колонка схемы: `enc` или `plain` с причиной, во ВСЕХ путях записи; AES-GCM (IV, tag, ключ, fallback, поведение при провале); `deleteAllUserData` против всех ссылок на пользователя (therapistId, clientId, партнёр, брони, события); merge переносит всё; логи и алерты без текста/токенов; телеметрия третьих сторон; бэкапы шифруются до загрузки; CI не печатает секреты | сверка реестров тестом |
| E. Фронтенды | токены только в памяти; ключи `localStorage` с клиническим текстом — чистятся при выходе и смене пользователя; SW не кэширует `/api`; XSS (DOMPurify, href, SVG); третьи скрипты (Метрика на клинических экранах, webvisor); postMessage origin; seam MAX/TG; кризисный путь на каждом свободном тексте; отчёты об ошибках без текста | тесты-инварианты в `webapp/src/security`, `shared/` |
| F. Инфраструктура и бот | helmet/CSP/HSTS/Referrer/Permissions-Policy; `trust proxy` и реальный IP для лимитов; фильтры ошибок без деталей Prisma; `/health` без лишнего; каждая команда/callback бота: `ADMIN_ID`, валидация `callback_data`; Docker (user, pinned image); зависимости (`npm audit --omit=dev` во всех пакетах) | таблица хендлеров + спеки |

Автоматика поверх: `npm audit` по четырём пакетам, grep антипаттернов из
плейбука §8, прогон существующих трипваеров `src/security/*.spec.ts`.

## Как решаем, что делать с находкой

1. **Critical/High** (чужие данные читаются или пишутся, захват сессии,
   обход роли) — чинится в этом же проходе, с регрессионным тестом, который
   воспроизводит сценарий атаки и падает до фикса.
2. **Medium** (ослабление защиты без прямого доступа: отсутствие лимита,
   PII в логе, слабая энтропия) — чинится в этом проходе, если фикс
   локальный; иначе — строка в «Что осталось открытым» с путём и доказательством.
3. **Low/Info** — трипваер или запись в принятые риски §13 плейбука с причиной.
4. Каждая находка — строка в [AUDIT_FINDINGS.md](AUDIT_FINDINGS.md) со статусом.
   Класс, которого нет в трипваерах, получает трипваер, а не только фикс
   (правило №20: «как система узнала бы об этом сама?»).

## Границы

Не входит: пентест живого прода (нет стенда с согласованным окном),
социальная инженерия, физическая безопасность устройства владельца,
юридическая оценка 152-ФЗ (отдельный документ).
