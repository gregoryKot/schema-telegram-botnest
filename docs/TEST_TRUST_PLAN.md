# План укрепления доверия к тестам (2026-08)

Продолжение `TEST_IMPROVEMENT_PLAN.md` (закрыт: 14/14 этапов, 2334 теста
бэкенда, 81.3% строк, 14 CI-гейтов). Тот план решал вопрос «сколько кода
покрыто». Этот решает вопрос **«можно ли верить зелёному CI»** — он
дороже: 2334 честных теста лучше 4000 самоуспокаивающих.

Порядок пунктов — по риску (вред × вероятность), а не по удобству.

## 1. Фейковая Prisma под всеми e2e — врёт, и мы это уже ловили

**Проблема.** 77 из 79 e2e работают на самописной имитации Prisma
(`test/e2e-support/fake-prisma.ts`). За время работы над планом она трижды
расходилась с настоящей — и каждый раз тесты были ЗЕЛЁНЫЕ:

- не понимала `OR` на верхнем уровне → `disconnect` «успешно» удалял 0 строк;
- не применяла `@default` из схемы → invite/join молча отбивался;
- не поддерживала `include` → связь `TherapyRelation → User` была `undefined`.

Три найденных — это те, на которые случайно наступили. Класс бага «тестовый
двойник врёт» опаснее дыры в покрытии: он делает зелёный CI недостоверным.
Единственный тест на реальном Postgres — `read-after-write` (2 кейса).

**Что делаем.** Ключевые e2e гоняются ВТОРЫМ прогоном против реального
Postgres в джобе `migrations` (инфраструктура уже поднята):
- `app-ownership`, `app-ownership-sweep*`, `therapy-ownership*` — они как раз
  про фильтрацию по `userId`, то есть ровно про то место, где фейк врал;
- `PrismaService` подключается к БД джобы, миграции уже применены;
- сначала — только эти спеки; остальные (auth-flows с моками jose и т.п.)
  остаются на фейке, это осознанно.

**Механизм.** Расхождение фейка с реальной БД теперь падает в CI, а не живёт
годами. Плюс: набор, гоняемый на реальной БД, может только расти — фиксируем
списком в workflow.

## 2. Честность 2300 тестов не измерена

**Проблема.** Mutation-замер сделан только для 4 файлов золотых зон. Там до
работы было **71%** — то есть примерно каждая третья «покрытая» строка не
была защищена. Остальные ~2300 тестов на честность не проверялись вообще;
оснований считать, что там лучше, нет. Покрытие 81% — верхняя граница,
реальная защита ниже.

**Что делаем.** Расширяем `mutate` в `stryker.config.json` волнами по 3-4
сервиса, в порядке цены ошибки:
- волна А: `merge.service` (перенос данных между аккаунтами — ошибка = потеря
  данных), `therapy-relations.service` (privacy), `telegram-auth.guard` (вход);
- волна Б: `notification.planner`, `subscription.lifecycle`, `booking.service`;
- волна В: `bot.service`-семейство.

Прогон — в nightly (в PR-CI ему не место). Каждая волна: замер → разбор
выживших → фиксация бейслайна.

## 3. Фронтенд: пользователь видит именно его

**Проблема.** Бэкенд 81.3%, miniapp ~23%, webapp **13.4%**, shared ~9%.
Компонентных тестов — десятки на ~200 компонентов в каждом фронте. `api`
мокается целиком, поэтому дрейф мока от реального клиента ловит только
TypeScript.

**Что делаем.**
- компонентные тесты на пути, где ошибка стоит денег или доверия: оплата,
  запись к терапевту, дневники, экспорт данных, удаление аккаунта;
- контрактный тест мока: проверка, что мокнутые методы `api` существуют в
  реальном клиенте с той же сигнатурой (тест-сверка, как `table-registry`);
- цель волны — webapp 13.4% → 25%, miniapp 23% → 32%.

## 4. Ни один тест не открывает приложение целиком

**Проблема.** Есть юниты, компонентные и HTTP-e2e. Нет теста, который
проходит пользовательский путь через реальный UI (браузер) — «зашёл, отметил
потребность, увидел её завтра».

**Что делаем.** Playwright уже стоит в окружении. Один smoke-путь на webapp:
логин-заглушка → трекер → сохранение → перезагрузка → значение на месте.
Не «покрытие», а страховка от «собралось, но не работает».
