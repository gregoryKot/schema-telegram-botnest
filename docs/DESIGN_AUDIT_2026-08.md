# Дизайн-аудит 2026-08

Полный аудит дизайна обоих фронтендов: визуальная система, UX мини-аппа, UX
сайта, доступность, консистентность webapp ↔ miniapp. Пять параллельных
проходов по коду; все находки уровня «критично» перепроверены вручную по
исходникам (файл:строка в каждой указаны).

Формат тот же, что у [PROJECT_AUDIT.md](archive/PROJECT_AUDIT.md): находка →
доказательство → что делать. Приоритет — в разделе «План» в конце.

## Критично

### К1. Живой баг «ты/вы»: отклик «Злой Ребёнок» в мини-аппе без `tr()`

`schema-miniapp/src/components/schemaFlashcard/constants.ts:24-25` — из всех
режимов флешкарты только этот отдаёт сырую строку с «Давай выясним», остальные
обёрнуты в `tr()`. Пользователь с формой «вы» видит «ты»-текст. В webapp тот же
контент обёрнут правильно (`webapp/src/components/SchemaFlashcard.tsx:28`) —
то есть фикс в своё время доехал до одного фронтенда из двух. Классика
правила №3: контент задублирован (webapp — инлайн в `SchemaFlashcard.tsx`,
miniapp — `schemaFlashcard/constants.ts`), копии правились независимо, даже
тире в них уже разное («–» против «—»).

**Что делать:** обернуть строку в `tr()`; следом перенести `buildModes` /
`NEEDS` / `STEPS` в `shared/src` — пока контент живёт в двух файлах, этот баг
будет возвращаться.

### К2. Экран `/auth/error` («Что-то пошло не так») не шлёт отчёт наверх

`webapp/src/App.tsx:161-189` — компонент `AuthError` не вызывает
`useAuthFailureReport`. Это буквальный пример из правила №14 («новый
экран-тупик … приезжает с отчётом наверх»), и на него реально стекаются
несколько классов сбоев Telegram-логина
(`webapp/src/pages/TelegramWidgetCallback.tsx:29,45,66,106,108`:
`telegram_no_data`, `telegram_decode_error`, `http_*`,
`telegram_unexpected_response`, `telegram_failed`). Инцидент 2026-08-08 —
пять суток молчаливо сломанного входа — случился ровно из-за такого молчания.

Рядом второй пробел того же класса: в `useBootstrapLoad.ts:62-75` catch
самого блокирующего запроса (`needs`/`ratings`, без него весь AppShell —
экран «Не удалось загрузить», `AppShell.tsx:233-243`) делает только
`setError`, тогда как остальные десять источников в том же файле корректно
попадают в общий отчёт (`useBootstrapLoad.ts:129-134`).

**Что делать:** подключить `useAuthFailureReport` в `AuthError` (передать
`reason` из query), добавить `fail('needs/ratings')` в catch bootstrap-загрузки.

### К3. Тап-цели ниже 44×44 — системно, и худший случай деструктивный

Стандарт в проекте есть (`GearButton`, `CustomizeButton`, `UpdateToast.tsx:64-70`
с комментарием «цель нажатия ≥44×44»), но в служебных оверлеях он не применён:

- `schema-miniapp/src/components/PracticesList.tsx:75-89` — **удаление
  практики: цель 30×30, подтверждения нет** (`usePracticesData.ts:61-65`
  зовёт `api.deletePractice` сразу, undo нет). Случайный тап = потеря данных.
- `TrackerOverlay.tsx:250-353` — «Закрыть», «Заметка», «История» по 34×34.
- `PracticesScreen.tsx:71-81` — «‹» назад: span без width/height, зона ≈26×26.
- `PlansScreen.tsx:64-82` — «‹» назад 34×34.
- Точки-переключатели шагов 8×8: `Disclaimer.tsx:80-97` (первый обязательный
  экран каждого пользователя) и `today/OnboardingWidget.tsx:264-296`.
- В webapp: крестики `ModeMapNodeEditor.tsx:591-594` (≈20px),
  `ModeMapGuide.tsx:114`.

**Что делать:** расширить хитбоксы padding'ом до 44×44 (визуально можно
оставить компактно — образец `UpdateToast`); удалению практики — шаг
подтверждения.

### К4. Шиты не оформлены как диалоги — ни один из ~70

`role="dialog"` / `aria-modal` в терапевтической части приложения — ноль
(в webapp только `CookieBanner` и мобильное меню лендинга; в miniapp — нигде).
Базовый `schema-miniapp/src/components/BottomSheet.tsx` (31 использование):
Escape есть, но нет `role="dialog"`, нет фокус-трапа (Tab уходит на фон под
шитом), нет возврата фокуса после закрытия — `activeElement` по всему коду
встречается только в тестах, то есть паттерна «вернуть фокус» нет ни в одной
модалке. Для скринридера в Telegram WebView открытый шит неотличим от фона.

**Что делать:** добавить в `BottomSheet` (и webapp-аналоги оверлеев)
`role="dialog"` + `aria-modal="true"` + фокус-трап + возврат фокуса — один раз
в базовых компонентах, разъедется по всем 70 местам само.

### К5. Контраст `--text-faint` ≈ 2.6:1 — не проходит WCAG, 500+ использований

`--text-faint: rgba(28,25,22,0.42)` на фоне `#f5f2eb` даёт ≈2.6:1 (норма AA
для мелкого текста 4.5:1, для крупного 3:1); на тёмной теме ≈3.2:1 — тоже
ниже нормы. Используется 312 раз в webapp и 194 в miniapp, включая **все
плейсхолдеры форм** (`index.css:192`) и подписи полей. Для аудитории с
СДВГ/тревожностью низкий контраст — прямая когнитивная нагрузка. `--text-sub`
(0.62) при этом проходит — ≈4.7:1.

**Что делать:** поднять альфу `--text-faint` примерно до 0.55 (light) и
проверить тёмную тему; это правка двух строк в двух `index.css`, эффект — по
всему продукту сразу.

## Важно

### В1. Шрифты 7–9px — подпороговый текст в десятках мест

Худший случай — `schema-miniapp/src/sections/today/NeedMini.tsx:95`:
`fontSize: 7`. В webapp — `fontSize: 8` в `ProfileSection.tsx:282,290,383`,
`8.5` в `ModeMapNodeEditor.tsx:263`, и десятки мест 9–11px в обоих проектах.
Даже официальная шкала `.text-xs` — 11px (miniapp) / 11.5px (webapp).

**Что делать:** нижний порог 11px для любого читаемого текста; свип по
`fontSize: [0-9]\b` с заменой 7–9 → 10–11.

### В2. Кризисный путь на сайте слабее, чем в мини-аппе

Вкладка «Помощь» (кризисная карта + 10 инструментов + задания терапевта) —
только в miniapp (`sections/HelpSection.tsx`), постоянная 4-я вкладка. На
сайте кризисная карточка появляется только реактивно — по срабатыванию
`crisisMarkers` в тексте. Постоянного «спасательного круга» у веб-пользователя
нет. Упражнение «Проверка фразы» тоже miniapp-only, хотя логика уже лежит в
`shared/src/phraseCheck/`, а `api.getPhraseChecks()` в webapp объявлен и
нигде не вызывается — выглядит как незавершённая работа, не решение.

**Что делать:** принять явное решение. Либо перенести «Помощь» (или хотя бы
постоянную точку входа к кризисной карте) и «Проверку фразы» на сайт, либо
задокументировать в CLAUDE.md как осознанное платформенное ограничение.

### В3. Ложный аффорданс закрытия у неотключаемых шитов

`BottomSheet` всегда рисует drag-ручку, вешает `pressable(onClose)` на
backdrop и один раз показывает подсказку «как закрыть» (`BottomSheet.tsx:42-58,
65-75, 116-133`). Но `CheckInSheet.tsx:41` и `Disclaimer.tsx:70` передают
`onClose={() => {}}` — закрытие отключено, а все аффордансы остаются и молча
не работают. Disclaimer — первый экран каждого пользователя; глобальный
`HINT_KEY` может потратить единственный показ подсказки именно на шит, где
закрытие не работает.

**Что делать:** флаг `dismissable={false}` в `BottomSheet`: прячет ручку, не
вешает обработчик на backdrop, не тратит подсказку.

### В4. На мобильном лендинге нет навигации — совсем

`ProductLandingPage.tsx:286`: `@media (max-width: 640px) { .pl2-nav
{ display: none !important; } }` — без бургера-замены (у второго лендинга,
`landing/nav.tsx:43`, `MobileMenu` есть). На телефоне в шапке главного входа
в продукт остаются логотип и «Войти»; ссылки на `/tests` (лид-магнит) и
статьи — только докручиванием до футера.

**Что делать:** мобильное меню по образцу `MobileMenu`, либо продублировать
«Тесты»/«Статьи» в hero.

### В5. Ошибка OAuth молча теряется на `/login`

`AuthCallback.tsx:54` шлёт на `/login?error=no_token`, но `LoginPage` query
не читает — после неудачного OAuth пользователь видит обычный экран входа без
объяснений, и ошибка никуда не репортится.

**Что делать:** читать `error` в `LoginPage`, показывать текст, репортить.

### В6. `AddressFormPicker` — единственный оверлей без `useHistorySheet`

`webapp/src/components/AddressFormPicker.tsx:43` — `position: fixed, inset: 0`,
рендерится глобально (`App.tsx:67`, в `RequireAuth`), хука нет. Кнопка «Назад»
браузера при открытой модалке уводит навигацию под ней. Остальные ~54 оверлея
правило соблюдают — нарушение одно.

### В7. Формы дневника без label — только placeholder

В miniapp `htmlFor` — 0 использований, `<label>` — 2. Формы дневника
(`DiaryTextArea.tsx`, в webapp `GratitudeEntrySheet.tsx:91`,
`ModeEntryForm.tsx:122,135`) связывают вопрос с полем только плейсхолдером;
видимый вопрос («Что бы сказал твой Здоровый Взрослый?») — отдельный div, с
textarea программно не связан. Плейсхолдер исчезает при вводе — человек с
рабочей памятью «на пределе» теряет вопрос. Корректные связки есть только на
периферии (BookingPicker, админка).

**Что делать:** `aria-labelledby` на видимый вопрос — минимальная правка в
`DiaryTextArea` и парных формах webapp.

### В8. Заголовков в мини-аппе нет: h1 — 2 шт., h2/h3 — 0

В webapp — 65/39/63 (h1/h2/h3), в miniapp — 2/0/0: заголовки экранов и шитов
— div со стилями (`NeedSheetHeader.tsx:54-65`, `SettingsSheet.tsx:187`).
VoiceOver/TalkBack в Telegram WebView не может ходить по заголовкам — только
линейно листать весь DOM. Основной ежедневный интерфейс аудитории — как раз
miniapp.

**Что делать:** заменить div-заголовки на h1/h2/h3 (стили не изменятся) —
начать с заголовков секций и базовых шапок шитов (`NeedSheetHeader`,
`SheetIconHeader`, `IntroSheetHeader`).

### В9. Слайдер «Колеса детства» недоступен с клавиатуры полностью

`schema-miniapp/src/components/childhoodWheelSheet/Slider.tsx` — чисто
pointer-based div: без `role="slider"`, `tabIndex`, `aria-value*`, стрелок.
Единственный способ поставить значение в упражнении. Контраст: `NeedRatingBar`
сделан образцово (10 нативных кнопок с `aria-label`/`aria-pressed`).

**Что делать:** либо перевести на `NeedRatingBar`-подход (правило «одна
механика — один компонент» — это второй слайдер в проекте), либо добавить
клавиатурную модель.

### В10. Разошедшиеся парные компоненты: функции теряются по дороге

Сверка 82 одноимённых пар. Кроме К1, поведенческие дыры:

- `NeedTodaySheet` (webapp): проп `yesterdayValue` объявлен, но не
  используется — маркер «вчера» на шкале видит только miniapp. Тексты CTA и
  affirmation разные при одной механике.
- `PlanSheet`: `.ics`-экспорт («Добавить в календарь») только в miniapp;
  зато баннер `practicesFailed` при отказе загрузки — только в webapp, в
  miniapp `console.error` и молча куцый список.
- `ShareCardSheet`: проп `therapyNote` (заход на терапию после «Поделиться»)
  существует только в miniapp — 5 точек шаринга; воронка к терапевту на сайте
  слабее.
- `CURATED`-практики задублированы дословно (`webapp/.../practiceCurated.ts`
  против инлайна в miniapp `PlanSheet.tsx`), пунктуация уже разошлась.
- Privacy-текст в настройках сформулирован по-разному («Данные не продаются и
  не передаются. Никогда.» против «…рекламным сетям или третьим лицам…») —
  доверительное заявление стоит сделать дословно единым.

**Что делать:** `CURATED` и `buildModes` → `shared/src`; `yesterdayValue`,
`practicesFailed`, `therapyNote` — досинхронизировать; по `.ics` — решить
осознанно.

### В11. Дизайн-токены декларированы, но вёрстка живёт мимо них

- `style={{` — ~2930 вхождений в webapp и ~2195 в miniapp: инлайн-стили —
  основной способ вёрстки, `index.css` с токенами и классами используется
  фрагментарно.
- Радиусы: у webapp токены `--r-sm/md/lg`, в компонентах — 23 разных инлайн-
  значения; у miniapp `--r-*` нет вообще, 20 разных значений.
- Цвета: 49 (webapp) + 31 (miniapp) уникальных hex вне токенов, 103+61
  rgba-литералов. Внутри самого `index.css` рассинхрон: `.chip-success/warn/
  danger` (строки 502–504) хардкодят rgba вместо `color-mix` с токеном — фон
  чипов не следует за тёмной темой; палитра аватаров `.av-1…8` (594–601) не
  переопределена в dark.
- Spacing-шкалы нет ни в одном проекте (`--space-*` — ноль), padding — 208
  (webapp) / 165 (miniapp) уникальных вариантов.
- Общих токенов между фронтендами 24 из 48/35 — даже имена разные
  (`--c-rose` против `--accent-red`), в `shared/` нет ни одного css/токен-файла.
  Разные акценты и шрифты (индиго+Inter против терракоты+Manrope) — судя по
  комментариям, осознанный выбор, но контракт нигде не зафиксирован.

**Что делать:** не переверстывать всё, а (1) зафиксировать в `shared/`
минимальный контракт имён токенов; (2) завести шкалы радиусов/отступов в оба
`index.css`; (3) починить `.chip-*` и `.av-*` через `color-mix`; (4) правило
на ревью: новый компонент — классы/токены, не инлайн-литералы.

## План: что чинить в каком порядке
