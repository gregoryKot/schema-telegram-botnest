# Инцидент 2026-08-08: вход не работал у всех пользователей Telegram

Пять суток мини-апп не пускал внутрь ни одного пользователя Telegram. Узнали
от человека, который прислал скриншот в личку. Ни один тест, гейт, лог и алерт
не сработал.

## Что видел пользователь

Экран «🔐 Не удалось войти» с текстом про **MAX** — мессенджер, которым он не
пользуется, — и кнопкой «Обновить», которая ничего не чинила.

## Хронология

| Когда | Что |
| --- | --- |
| 03.08, PR #245 | В `schema-miniapp/index.html` добавлен `<script src="/max-bridge.js">` — загрузчик моста площадки MAX. С этого момента вход из Telegram сломан у всех. |
| 03.08 — 08.08 | Пять релизов, зелёный CI, ноль сигналов. Пользователи Telegram видят экран ошибки. |
| 08.08, ~12:20 | Владелец приносит скриншот. Причина найдена за ~10 минут, фикс #298 смержен в 12:30. |
| 08.08, ~12:35 | Сборка на Amvera падает: билдер не достучался до deb.debian.org на `apt-get install openssl`. Фикс не доезжает до прода. |
| 08.08, ~13:05 | Сборка починена (#299), прод отдаёт исправленный `max-bridge.js`. |

## Причина

`webapp/public/max-bridge.js` определял «мы внутри MAX?» так:

```js
if (window.location.hash.indexOf('WebAppData=') === -1) return;
```

Telegram передаёт свои стартовые данные тем же фрагментом адреса —
`#tgWebAppData=…`. Внутри этого имени **подстрока `WebAppData=` есть**. Дальше
по цепочке:

1. загрузчик подключал мост MAX при каждом запуске мини-аппа из Telegram;
2. их SDK безусловно создаёт глобаль `window.WebApp` (проверено на живом
   `st.max.ru/js/max-web-app.js`: `window.WebApp = b`);
3. `detectHostId()` проверял мост MAX ПЕРВЫМ и отвечал `'max'`;
4. приложение отправляло заголовок `x-max-init-data` с пустым значением —
   максовской подписи в телеграмном запуске взяться неоткуда;
5. guard получал пустую строку, она falsy → запрос проваливался в финальное
   `throw new UnauthorizedException('Missing authentication')`;
6. экран ошибки брал имя мессенджера у хоста — и говорил «MAX».

Ошибка была ровно в одной строке. Но чтобы она прожила пять дней, должны были
одновременно промолчать четыре разных слоя защиты.

## Почему не поймали

### 1. Браузерный код вне `src/` был вне всех инструментов

`public/max-bridge.js` никто не импортирует. Значит:

* **coverage** его не видит (`include: ['src/**']`);
* **гейт мёртвых файлов** не видит (ходит по `.ts/.tsx` в `src`-деревьях);
* **тесты** его ни разу не исполняли — до 08.08 ни один тест репозитория не
  упоминал ни один файл из `public/`;
* **eslint** файл проверял и был доволен: поиск подстроки — валидный код.

Двадцать строк, выполняющихся у каждого пользователя, ехали в прод вообще без
проверки. Это не «забыли написать тест» — это «инструменты физически не могли
его увидеть».

### 2. Тесты стояли по обе стороны шва, но не на самом шве

`shared/src/host/host.test.ts` покрывал `detectHostId()` подробно — 62 теста.
Но `window.WebApp` в них ставили **руками**, то есть тест кодировал допущение
«этот объект бывает только в MAX». Ошибка была именно в том, что допущение
перестало быть верным: его нарушил другой файл, которого в тесте нет.

Зелёные тесты по обе стороны границы не проверяют границу.

### 3. Сломанный вход не поднимал тревогу на сервере

Пустая подпись проваливалась в ветку `Missing authentication` — без лога,
счётчика и алерта. Для сервера авария выглядела как фоновый шум
неавторизованных запросов, которого всегда много.

### 4. Телеметрия фронта была только у крашей

`reportClientError` слал наверх падения `ErrorBoundary`. А сломанный вход
крашем не был: приложение аккуратно ловило 401 и рисовало обработанный экран.
**Обработанная авария оказалась невидимее необработанной.**

### 5. Сломанный вход не виден в метриках

`/stats` показывает продуктовые события. Событие «человек вошёл» не пишется
(вход — не фича), поэтому падение входа до нуля не отражалось ни в одной
строке отчёта.

## Что сделано, чтобы не повторилось

Правила без механизма не работают, поэтому каждый пункт — код в CI или тест.

| Дыра | Механизм |
| --- | --- |
| Код вне `src/` без проверки | **`scripts/check-public-scripts.mjs`** (CI, джоба `checks`): каждый `public/**/*.js` обязан упоминаться тестом; инлайн-`<script>` в index.html заморожены по хешу содержимого. Исключения — `public-scripts-baseline.json` с причиной, протухшая запись роняет гейт. Сам гейт покрыт `src/test-support/gates/public-scripts.spec.ts` (оба исхода). |
| Тесты не на шве | **`webapp/src/hostDetection.seam.test.ts`**: настоящий адрес запуска → настоящий файл загрузчика → настоящий `detectHostId()`. Проверено, что на старом коде тест краснеет. Плюс `webapp/src/maxBridgeLoader.test.ts` на сам загрузчик. |
| Тихий отказ входа на сервере | **`src/api/auth-failure.report.ts`**: пустая подпись отделена от «просто неавторизован» — DM админу (троттлинг 15 мин на площадку) + событие `auth_rejected`. Обычный анонимный запрос по-прежнему молчит, иначе алерт утонет в шуме. Регресс — в `telegram-auth.guard.spec.ts`. |
| Немой экран ошибки | **`useAuthFailureReport`** в `shared/` (правило №3, один хук на оба фронта): экран неудачного входа сам отправляет отчёт с площадкой и признаком пустой подписи. Значений подписи наружу не уходит. |
| Авария не видна в отчёте | **Блок «Вход в мессенджере» в `/stats`** (`auth-health-metrics.*`): сколько раз за сутки и за неделю приложение приходило без пропуска. Считаются только серверные строки (`userId IS NULL`) — накрутить с клиента нельзя. |
| Сборка падает — фикс не едет | **`deploy/install-openssl.sh`** (#299): три попытки, запасное зеркало, обязательная проверка `openssl version`. |

## Уроки, которые стоит помнить

1. **«Никто не импортирует» = «никто не проверяет».** Любой код, который
   исполняется у пользователя, обязан быть виден хотя бы одному инструменту.
2. **Совпадение подстроки — не проверка имени.** `indexOf('X=')` находит `Y_X=`.
   Имя параметра, ключа, заголовка сверяется целиком.
3. **Тест, который сам ставит предусловие, проверяет только своё допущение.**
   Если предусловие создаёт другой файл — тест обязан пройти через него.
4. **Обработанная ошибка опаснее необработанной**: краш видно, аккуратный
   экран — нет. У каждого экрана-тупика должен быть отчёт наверх.
5. **Зелёный CI не значит «у пользователей работает».** Между зелёным CI и
   пользователем есть сборка, деплой и живой клиент — и на каждом участке
   нужен свой сигнал.
