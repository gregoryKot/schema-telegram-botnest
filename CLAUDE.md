# Правила проекта

## Правила по итогам аудита 2026-07 (см. [docs/archive/PROJECT_AUDIT.md](docs/archive/PROJECT_AUDIT.md))

Каждое правило ниже закрывает конкретный класс найденных проблем. Принцип:
**правило без механизма принуждения не работает** — где возможно, правило
дублируется проверкой в CI/тесте.

### 1. Ничего не мержится с красным CI
Каждый PR проходит: `tsc --noEmit` + `jest` + `eslint` + сборки обоих
фронтендов + vitest + **`migrate deploy` на реальном Postgres** (джоба
`migrations`). Ручной запуск тестов «по памяти» — не защита: до июля
2026 в проекте было 144 зелёных теста, которые никто не запускал перед деплоем.

### 1а. Мержит агент, не владелец
Владелец проекта PR-ы **не мержит**. Агент, открывший PR, сам доводит его до
конца: дожидается CI, при красном — чинит и перезапускает, при полностью
зелёном — снимает драфт и мержит (squash) без дополнительного вопроса.
Мерж в `main` = деплой (Amvera тянет из GitHub автоматически), поэтому
«запушил и ушёл» — не завершённая работа: фикс не существует для
пользователя, пока не смержен. Исключение — PR помечен `do-not-merge`
или в описании явно сказано «не мержить».

### 2. Правило тестов распространяется на фронтенды
«Любой новый код с логикой обязан приезжать с тестом» действует и для
webapp/miniapp (vitest + testing-library), а не только для `src/*.spec.ts`.
Логика = ветвления, вычисления, работа с данными. Чистый JSX/стили — нет.

### 3. Парные файлы правятся парой (webapp ↔ miniapp)
Если файл имеет двойника во втором фронтенде — фикс вносится в **оба в одном
PR**, либо файл переносится в shared-пакет. Найдено 3+ случая, когда фикс
(ты/вы, рефакторинг) доехал только до одного фронтенда. Новый общий код —
сразу в shared, а не копипастой.

Контент-файлы одной сущности (`needData`, `YsqSyncErrorNote`) уже переехали в
`shared/src/` — для них правило «правь оба» больше не действует: источник
один, а `webapp/src/needData.ts` и `schema-miniapp/src/needData.ts` — тонкие
ре-экспорты, не копии. Новый общий контент между фронтендами — сразу в
shared, а не по образцу старого дубля.

### 4. Денормализация и дублированные реестры — только с тестом-сверкой
Любые два места, обязанные совпадать (`USER_DATA_TABLES` ↔ `USER_OWNED_TABLES`
↔ schema.prisma; `mySchemaIds` ↔ `UserSchemaNote`), фиксируются тестом,
который падает при рассинхроне. Read-modify-write по денормализованному
полю — только в `$transaction` или через пересчёт из источника правды.

### 5. Идентичность для rate-limit — только верифицированная
Троттлинг-бакет строится по проверенной подписи (JWT/initData). Всё
неверифицированное бакетируется по IP (или `uid|ip`). Иначе лимит
обходится ротацией фейкового `sub`.

### 6. Новый эндпоинт = DTO с class-validator
Inline-интерфейсы в `@Body()` дают только compile-time иллюзию. Рантайм
валидируется декораторами DTO + глобальным `ValidationPipe({ whitelist: true })`.

### 7. Свободный текст от юзера = кризисный путь
Любая новая фича, принимающая свободный текст (дневник, заметка, письмо),
обязана проходить через кризисную детекцию (`crisisMarkers`) с карточкой
телефона доверия 8-800-100-49-94 (взрослая линия, продукт 18+; детская линия
8-800-2000-122 идёт второй строкой с подписью аудитории). Детекция — на
клиенте, до шифрования. Терапевтический продукт без кризисного пути —
недопустим.

### 8. Продуктовая фича = событие аналитики
Новая user-facing фича приезжает с событием в analytics (иначе её эффект
непроверяем). Гипотезы про онбординг/retention проверяются метриками
D1/D7/D30, а не ощущениями.

**Пайплайн событий** (единственный, не плоди второй): фронт шлёт
`api.trackEvent(name, meta)` (fire-and-forget, оба фронтенда — правило №3),
бэк принимает `POST /api/event` (`TrackEventDto` + `AnalyticsController`
санитизирует meta → `AnalyticsService.track` пишет в `AnalyticsEvent`).
Имена событий — allow-list `src/analytics/analytics.constants.ts`
(`ANALYTICS_EVENTS`); новое событие = имя в этот список + ветка в `sanitizeMeta`
(пропускать ТОЛЬКО известные поля — свободный текст/PII в meta недопустимы,
правило №7) + парная константа/тип на фронте (`shared/src/share/analytics.ts`).

**Каждая новая метрика/событие ОБЯЗАНА появиться в отчёте `/stats`.** Событие,
которого нет в отчёте, — невидимо: его будто нет. Механизм:
- агрегат — метод в `BotAnalyticsService` или в `ProductMetricsService`
  (`count()`/`groupBy` для таблиц, `$queryRaw` для группировки по `meta`);
- вывод — **чистый форматтер** (`formatProductMetrics`/`formatRetentionBlock`
  как образцы), который `/stats` подклеивает к тексту (`getAdminStats` или сама
  команда — при переполнении лимита Telegram 4096 шлётся двумя сообщениями);
  форматтер покрыт тестом, **обязательно и пустое состояние** — на чистой БД
  отчёт не должен показывать «0/NaN/мусор»;
- **язык отчёта — простой, без терминов** («поделились N раз», а не
  «share_card events»; «возвращаются ли новенькие», а не «cohort retention»).
  Пиши так, чтобы понял ребёнок; англицизмы/жаргон — в подписи словами.

Общий фронт-код события (трекинг-хук, share-хелпер) — сразу в `shared/`
(правило №3/№11): образцы — `shared/src/analytics/useCrisisCardTracking`,
`shared/src/share/shareCardWithTracking`.

Механизм принуждения (ревью): «новое событие видно в `/stats`? понятно без
словаря? есть тест на форматтер, включая пустую БД?». Нет — фича не готова.

### 9. eslint-храповик
Ни один PR не увеличивает счётчик ошибок eslint. `no-floating-promises` —
error. Новые `any` не добавляются (`no-explicit-any` как минимум warn);
каст Prisma-делегата на `any` запрещён — чини типы, а не глуши их.

### 10. Лимит размера файла — честный и всеобщий
~150 строк для нового кода, жёсткий потолок 300 (бэкенд и фронтенд).
Компонент реакта >300 строк — выноси хуки/подкомпоненты. Правило «один
сервис = один файл» не означает «один файл на 13 доменов».

Механизм принуждения (правило без гейта не работает — до июля 2026 это
правило было единственным в разделе без проверки, и 76+ файлов пробили
потолок, худший — 3386 строк):
- **`scripts/check-file-size-ratchet.mjs`** (CI, джоба `backend`) —
  пофайловый храповик. Файл из `scripts/file-size-baseline.json` может
  только **уменьшаться**: рост сверх зафиксированного размера роняет CI
  (раздутый файл дробится, а не пухнет дальше). Любой **новый** файл (не в
  бейслайне) не имеет права родиться больше 300 строк.
- Снизил размер — зафиксируй прогресс, чтобы файл нельзя было снова
  раздуть: `node scripts/check-file-size-ratchet.mjs --update`. Долг
  (файлы сверх 300) заморожен в бейслайне и обязан таять, а не расти.
- Исключения: `game/` (заморожён), `dist/`, `*.spec/.test`, `*.d.ts`,
  vendor. Крупный дата-файл (контент) — осознанное исключение через
  `--update`, видно в диффе PR.
- Гейт, упёршийся в потолок, дробится на движок + модуль правил
  (`*-patterns.mjs`/`*-rules.mjs`), а не получает исключение из храповика —
  образцы: `gendered-forms-patterns.mjs`, `silent-catch-rules.mjs`. Как
  песочница тестов подхватывает раздробленный гейт — см. «Тестовые
  храповики и e2e» ниже.

### 11. Дубли и мёртвый код — под гейтами (по итогам свипа 2026-07)
Свип нашёл: живые маршруты-дубли (`/api/settings` и client-notes в двух
контроллерах — отвечал тот, чей модуль раньше, у второго терялась
privacy-проверка `therapistShareCards`) и ~20 мёртвых файлов-копий
(старые версии секций, замещённые новыми — HelpSection/ExercisesSection
против PracticeSection). Механизмы:
- **`scripts/check-route-collisions.mjs`** (CI): один маршрут — один
  контроллер, второй регистрант = мёртвый код с расползающейся логикой.
- **`scripts/check-jscpd-ratchet.mjs`** (CI): счётчик дублированных строк
  (≥70 токенов) не растёт. Повторяешь блок — выноси в модуль/хук.
- **`scripts/check-dead-files.mjs`** (CI, джоба `checks`): у каждого файла
  обязан быть потребитель среди НЕ-тестовых файлов — во всех деревьях сразу
  (бэкенд, оба фронтенда, shared). Спек в потребители не годится: файл,
  который импортирует только его собственный тест, и есть мёртвый код
  (реальный случай 2026-08 — вторая копия `prisma-exception.filter`, куда
  ушла правка обработки ошибок, не доехавшая до прода). Исключения — в
  `scripts/dead-files-baseline.json` с причиной; протухшая запись (файл
  удалён или у него появился потребитель) тоже роняет гейт.
- Заменяя компонент/секцию новой версией — **удаляй старую в том же PR**
  (иначе jscpd считает её «дублем», а следующий редактор правит мёртвую).
- Периодически (раз в квартал / перед крупным рефакторингом):
  `npx knip --include files` по каждому пакету + грep-верификация. knip
  не видит script-теги и лениво-динамические импорты — удалять только
  после грепа.

### 12. Голос продукта — под гейтом (по итогам свипа 2026-07)

> Полный стиль-гайд — запрещённые конструкции, что обязательно, проверка
> готового текста — в [docs/VOICE.md](docs/VOICE.md). Читать перед написанием
> **любого** текста, который увидит пользователь.

Правила «не звучать как робот» жили в `docs/ARTICLES.md` и касались только
статей. Свип нашёл те же конструкции по всему продукту: в пуле канала
«Здоровый Взрослый» 18 фраз из 46 были построены на одном скелете «Это не X.
Это Y» — подряд пул читался как одна заготовка. Правило переехало в
`docs/VOICE.md` и действует для бота, уведомлений, мини-аппа, сайта и статей.

Коротко: определение через отрицание («это не X, это Y», «это не про А, это
про B») допустимо, только пока оно редкое и вторая часть даёт новое. Канцелярит
(«является», «представляет собой», «осуществляется»), метатекст («важно
отметить», «в целом»), слова-филлеры («ключевой», «эффективный», «уникальный»)
и служебные мостики между абзацами («таким образом», «тем не менее») —
запрещены. Исключение — юридические документы (`OfferPage`, `PrivacyPage`),
там формальные обороты юридически точны.

Механизм принуждения: **`scripts/check-robot-phrases.mjs`** (CI, джоба
`backend`) — пофайловый храповик. Счётчик конструкций в файле может только
уменьшаться, новый файл рождается с нулём. Снизил — зафиксируй:
`node scripts/check-robot-phrases.mjs --update`. Посмотреть, что именно
насчитано: `--verbose`.

### 13. Конфликты параллельных агентов лечатся механизмом, а не аккуратностью

Агенты работают параллельно от одного `main`, и конфликты у нас были не
случайные, а структурные: есть файлы, которые **обязан** тронуть почти каждый
PR. За 300 коммитов `scripts/file-size-baseline.json` менялся 44 раза,
`schema-miniapp/dist/index.html` — 27, coverage-бейслайны — по 20. Просить
агентов «быть аккуратнее» бесполезно: у скалярного бейслайна значимая строка
одна на весь файл, два поднявших покрытие агента конфликтуют **всегда**.

Хуже самого конфликта — как его разрешают. Агент берёт «свою» сторону и молча
откатывает чужой прогресс: планка храповика опускается, CI зелёный, никто не
замечает. То есть ручное разрешение конфликта в бейслайне почти всегда неверное.

Механизм — merge-драйверы (`.gitattributes` + `scripts/setup-merge-drivers.mjs`,
ставятся в `.git/config` из npm `prepare`, то есть сами на любом `npm install`):

- **бейслайны храповиков** сводятся `merge-json-ratchet.mjs` по семантике
  храповика: пер-ключ `min` там, где меньше лучше (размеры, робофразы, род,
  дубли), `max` для покрытия и mutation. Прогресс обеих сторон сохраняется,
  планка опуститься не может. Неоднозначное (разные строки-причины, битый
  JSON) драйвер не выдумывает — отдаёт обычный конфликт человеку;
- **`schema-miniapp/dist/**`** сводится `merge-miniapp-dist.mjs` в два шага.
  Бандл построчно не сливается, а собрать верный dist можно только когда
  слитый исходник уже лежит в дереве — то есть **после** слияния, не внутри
  него (проверено: сборка внутри драйвера взяла исходник без правки второй
  стороны, и в прекэше `sw.js` оказалась revision чужого бандла). Поэтому
  драйвер только гасит конфликт, а хук `post-merge` сразу пересобирает
  мини-апп и стейджит `dist` — остаётся `git commit --amend --no-edit`.
  Подстраховка, если хук не сработал (слияние с конфликтами в исходнике,
  свежий клон без `npm install`) — CI-джоба `miniapp`, она роняет PR при
  расхождении `dist` с исходником.
- **Имена ассетов мини-аппа — без контент-хеша** (`vite.config.ts`). С хешем
  у двух PR расходились *имена* файлов, и git ловил rename/rename — конфликт,
  который content-драйвер не чинит в принципе. Бастить хешем нечего:
  `ServeStaticModule` отдаёт статику с `max-age=0` и ETag. Инварианты (нет
  хеша в имени, нет `revision: null` в прекэше SW) — под
  `src/test-support/gates/miniapp-dist.spec.ts`.

Что из этого следует для работы:

- **Конфликтующий PR сводится локально, а не в браузере.** Кнопка «Resolve
  conflicts» в вебе GitHub про драйверы не знает: `git fetch origin main &&
  git merge origin/main`, потом пуш.
- **Новый бейслайн приезжает со строкой в `.gitattributes`.** Атрибут без
  драйвера молча деградирует до текстового слияния — сверка
  `node scripts/setup-merge-drivers.mjs --check` в джобе `checks` это ловит.
- **Файлы-реестры, где порядок не значим, держим отсортированными** —
  сортировка разводит вставки по файлу вместо общей точки в хвосте.
  Исключение: `USER_OWNED_TABLES` / `USER_DATA_TABLES` сортировать **нельзя**,
  там порядок задаёт FK-зависимости при удалении.
- **`package-lock.json` не сводят руками**: берётся любая сторона, дальше
  `npm install` перегенерирует.
- **Открыл PR — доводи его до мержа, не копи очередь.** Пять PR от одного
  `main` означают, что первый мерж делает конфликтными остальные четыре.
  Помогает `enable_pr_auto_merge` (GitHub сериализует очередь сам) и
  `update_pull_request_branch` перед мержем.
- **Параллельные миграции текстово не конфликтуют, но применяются по времени** —
  вторая обязана быть корректной поверх первой, а не поверх того `main`, от
  которого её писали.

Механизм принуждения: `setup-merge-drivers.mjs --check` в CI (джоба `checks`)
плюс `src/test-support/gates/merge-drivers.spec.ts` — тест проверяет ОБА
исхода, включая контрольный: без драйвера та же пара веток обязана
конфликтовать, иначе тест ничего не доказывает.

### 14. Всё, что исполняется у пользователя, обязано быть кем-то проверено

> Разбор целиком — [docs/archive/INCIDENT_2026-08-08_TELEGRAM_LOGIN.md](docs/archive/INCIDENT_2026-08-08_TELEGRAM_LOGIN.md).
> Регулярная проверка щита (что ещё никем не проверяется) — промпт
> [docs/SHIELD_PROMPT.md](docs/SHIELD_PROMPT.md): раз в квартал, перед крупным
> рефакторингом и после каждого инцидента, где поломку нашёл человек, а не
> система. Там же живут таблицы «что закрыто» и «известные дыры» — обновляй их
> в том же PR, что и новый механизм.

Пять суток вход в мини-апп не работал **ни у одного пользователя Telegram**.
Виновата одна строка в `webapp/public/max-bridge.js`: она искала во фрагменте
адреса ПОДСТРОКУ `WebAppData=`, а Telegram передаёт свои стартовые данные как
`#tgWebAppData=…` — подстрока совпала. Мост чужой площадки грузился у всех,
приложение считало себя открытым в MAX и слало пустую подпись.

Строка была одна, но чтобы прожить пять дней, промолчали четыре слоя:

- **Код вне `src/` не видел никто.** Файл в `public/` никто не импортирует —
  значит он вне coverage, вне гейта мёртвых файлов и вне тестов. Гейт:
  **`scripts/check-public-scripts.mjs`** (CI, джоба `checks`) — каждый
  `public/**/*.js` обязан упоминаться тестом (образец —
  `webapp/src/maxBridgeLoader.test.ts`: читает файл с диска и исполняет с
  поддельными `window`/`document`), инлайн-`<script>` в index.html заморожены
  по хешу. Исключение — причина в `scripts/public-scripts-baseline.json`.
- **Тесты стояли по обе стороны шва, но не на шве.** `detectHostId()` был
  покрыт 62 тестами, только `window.WebApp` в них ставили руками — тест
  кодировал допущение «этот объект бывает только в MAX», а сломал допущение
  соседний файл. **Если предусловие в проде создаёт другой код — тест обязан
  пройти через него** (`webapp/src/hostDetection.seam.test.ts`: настоящий
  адрес запуска → настоящий загрузчик → настоящий детектор).
- **Отказ входа молчал на сервере.** Пустая подпись падала в ветку
  `Missing authentication` без лога и счётчика. Теперь «мессенджер открыт, а
  подписи нет» — отдельный случай: DM админу + событие `auth_rejected`
  (`src/api/auth-failure.report.ts`). Обычный анонимный запрос по-прежнему
  молчит: алерт, тонущий в шуме, — это не алерт.
- **Телеметрия фронта была только у крашей.** Сломанный вход крашем не был:
  приложение аккуратно ловило 401 и рисовало экран. **Обработанная авария
  невидимее необработанной** — поэтому у экрана-тупика обязан быть отчёт
  наверх (`useAuthFailureReport` в `shared/`, оба фронта).

Что из этого следует для работы:

- **Совпадение подстроки — не проверка имени.** `indexOf('X=')` находит `Y_X=`.
  Имя параметра, ключа, заголовка сверяется целиком (`/(^|[#&])X=/`).
- **Новый экран-тупик («не удалось войти», «нет доступа», «что-то пошло не
  так») приезжает с отчётом наверх.** Иначе о поломке узнаешь от пользователя.
- **Новая сигнализация приезжает с троттлингом.** Авария — это поток; сотня DM
  подряд = замьюченный чат, то есть ноль алертов (тот же урок, что 2026-07-29).
- **Здоровье входа видно в `/stats`** — блок «Вход в мессенджере»
  (`auth-health-metrics.*`). Считаются только серверные строки
  (`userId IS NULL`), накрутить с клиента нельзя.
- **Зелёный CI не значит «у пользователей работает».** Между CI и человеком
  есть сборка, деплой и живой клиент мессенджера — на каждом участке нужен
  свой сигнал.

### 15. Гейт не замалчивают — его чинят (по итогам серии свипов 2026-08)

Гейт молчит по двум причинам: нарушение исправлено или нарушение спрятано.
Со стороны CI это неразличимо, и в серии из семи PR вторая причина случилась
у нас **четыре раза** — каждый раз добросовестно, «чтобы стало зелёно».

Как выглядит замалчивание на практике:

- **Обход формулировкой.** Строку не разводят по формам, а переписывают так,
  чтобы паттерн не сматчился: «Проверь подключение» → «Стоит проверить
  подключение». Гейт доволен, пользователь с формой «вы» по-прежнему видит не
  своё, а текст стал казённее. Отдельный подвид — обезличивание: оно убирает
  того, кто действует, и в юридическом тексте меняет смысл («соглашение даёт
  отдельное согласие» — согласие вдруг даёт документ, а не человек).
- **Исключение без разбора.** Файл вносят в `ALLOW`/`EXCLUDE`, потому что он
  «похож на законный». Так `LinkDevicePage` едва не уехала в исключения как
  «экран до входа» — на деле она требует авторизации, и её строки были живым
  багом.
- **Бейслайн вместо починки.** `--update` поверх выросшего счётчика без
  разбора, что именно выросло.
- **Переезд в слепую зону.** Код уводят туда, куда гейт не смотрит
  (`game/`, `public/`). Заморозка задумана как «не считать долг», а работает
  как «сюда никто не посмотрит»: в `game/` так сохранились тридцать мужских
  форм, включая публичный текст «поделиться».

Что делать вместо этого:

1. **Сначала спроси, почему гейт прав.** Он ловит класс, а не строку: если
   ругается на текст — вероятно, у строки правда нет формы обращения, а не
   «регэксп придирается».
2. **Исключение — только с обоснованием и контрольным тестом.** У каждой
   записи `ALLOW`/`EXCLUDE` в комментарии причина, а в тесте гейта — образец,
   который она гасит, И контрольный образец: похожий, но незаконный случай
   обязан по-прежнему краснеть. Образцы: «EXCLUDE не шире, чем нужно» в
   `second-person.spec.ts`, «у каждого ALLOW есть образец» в
   `robot-phrases.spec.ts`.
3. **Рост бейслайна объясняется в теле коммита** — что выросло и почему это
   неизбежно. Молчаливый `--update` вверх читается как замалчивание.
4. **Ложный долг разбирают, а не копят.** Гейт, чей замороженный остаток на
   две трети состоит из законного кода, не растает никогда — ему перестают
   верить и в итоге отключают. Калибровка (у нас 359 → 58 после разбора) —
   это не уборка, а спасение механизма.

Механизм принуждения: `scripts/check-gate-exemptions.mjs` (CI, джоба `checks`)
— у каждого списка исключений в `scripts/*` обязан быть тест, который его
загружает и пинит образцом. Плюс вопрос на ревью: «гейт молчит — потому что
починено или потому что обойдено?».

### 16. Паритет фич между фронтендами — по роутам бэкенда, не по файлам (по итогам расследования 2026-08-21)

Правило №3 требует, чтобы фикс/фича приезжали в оба фронтенда. Расследование
2026-08-21 нашло, почему это не срабатывало на практике: целые фичи
(упражнение «Критик или забота?», карточки шаринга режима/месяца/достижений,
`.ics`-экспорт плана) жили только в мини-аппе, и ни один существующий гейт
этого не заметил. Причина — оба защитных механизма смотрят не туда:

- `check-paired-files.mjs` ходит по жёсткому списку `PAIRS` (~20 записей) и
  сравнивает уже зарегистрированные пары побайтово. Файл, которого в списке
  нет, гейт не видит вообще — ни как расхождение, ни как рождение без пары.
  Защита держится на «не забыл добавить в PAIRS», то есть на памяти автора.
- `check-dead-files.mjs` считает единицей учёта ФАЙЛ, а не метод внутри
  него. Живой `api.ts` прикрывает собой мёртвый экспорт: `deleteBeliefCheck`,
  `deleteFlashcard`, `deleteLetter` объявлены в ОБОИХ фронтендах и не
  вызываются НИОТКУДА, кроме тестов, — файл живой, гейт молчит, а под
  готовыми роутами `DELETE /api/belief-checks/:id` и соседями нет ни одной
  кнопки удаления ни на одной площадке.

Оба механизма ловят только то, что кто-то заранее зарегистрировал руками.
**`scripts/check-feature-parity.mjs`** (CI, джоба `checks`) смотрит с другой
стороны — от источника истины, общего для обеих площадок: HTTP-роутов
бэкенда (`src/api/**/*.controller.ts`). Для каждого роута гейт проверяет, кто
его реально доступается — webapp, мини-апп, оба или никто (shared/src
засчитывается обеим площадкам: `buildSharedApi`/`createRatingApi` спред-ятся
в оба `api`-объекта). «Доступность» — не сам факт объявления метода в
`api.ts` (иначе гейт был бы вечнозелёным ровно там, где нашёлся баг с
`deleteBeliefCheck`), а то, что объявленный метод хоть раз упоминается за
пределами своей строки-объявления — не полная трассировка до конкретного
экрана, а минимальный сигнал «это не мёртвый стаб».

Что из этого следует для работы:

- Роут, доступный не с обеих площадок (или ни с одной), красит CI, если он
  не заведён в `scripts/feature-parity-baseline.json` с `status`, честной
  `reason` (не короче ~20 символов, не «legacy») и `since` (коммит/PR, где
  решение принято) — тот же принцип записи, что у `dead-files-baseline.json`.
- Платформенное решение (лид-магнит мини-тестов — только на сайте, запись на
  консультацию — тоже, быстрые практики «Здесь и сейчас» — пока только в
  мини-аппе) заводится в бейслайн как осознанное. Недоделка (объявленный, но
  нигде не вызванный метод; незаконченная миграция вроде черновиков
  `/api/drafts`, у которых бэкенд готов, а фронтенды по-прежнему пишут
  только в `localStorage`) заводится ЧЕСТНО — с причиной, называющей это
  долгом, ждущим решения владельца, а не мимикрирующей под платформенный
  выбор (правило №15: гейт не обходят удобной формулировкой).
- Запись протухает — роняет CI — если роут исчез из бэкенда или паритет уже
  не односторонний (кто-то фикс всё-таки довёз до обеих площадок, но забыл
  убрать запись). Протухшая запись — это не уборка, а сигнал «сверься, что
  на самом деле произошло».
- Новый эндпоинт, который заведомо должен остаться на одной площадке
  (админский, инфраструктурный вроде `/health`) — сразу с записью в бейслайн
  в том же PR, не постфактум.

## Делегирование моделям (правило для всех диалогов)

Основная (дорогая) модель сессии **планирует, ревьюит и отвечает за итог** —
но не пишет код руками, пока задача делегируема. Реализация по готовому плану,
механические правки, прогоны сборок/тестов отдаются субагентам на менее
дорогих моделях (Agent tool: `model: "sonnet"`; совсем механическое —
`"haiku"`). Дорогая модель формулирует точное ТЗ, принимает работу и
дочинивает только то, что дешёвой модели не удалось.

## Структура

- `src/bot/` — бизнес-логика (потребности, оценки, БД)
- `src/telegram/` — всё связанное с Telegram (команды, кнопки, провайдер бота)
- `src/prisma/` — PrismaService, подключение к БД

- `schema-miniapp/` — Telegram мини-апп `schemehappens.ru/app/` (initData)
- Оба ходят в один NestJS API. Данные **общие** если `userId` совпадает.

Когда совпадает:
- Telegram login на сайте ⇄ мини-апп = один и тот же `userId = telegramId` ✓
- Google login на сайте → отдельный web-only `userId`. Чтобы данные подтянулись из мини-аппа — юзеру надо в `/account` нажать "Привязать Telegram" и потвердить merge.

См. `src/auth/merge.service.ts` — транзакционный перенос userId по всем USER_OWNED_TABLES при подтверждённом merge.

**Новая функциональность** → сначала логика в `bot.service.ts`, потом UI в `telegram.service.ts`.
Не смешивай Telegram-логику с бизнес-логикой.

## Обращение «ты/вы» (ОБЯЗАТЕЛЬНО для любых новых текстов)

У пользователя есть выбор формы обращения — поле `User.addressForm` (`'ty' | 'vy'`,
дефолт при `null` = «ты»). Выбор делается при первом входе и меняется в настройках.
Действует **везде**: бот, уведомления, мини-апп, сайт. Данные общие — форма едина.

**Правило: каждая новая user-facing строка с обращением обязана звучать в обеих формах.**
Пользователь с формой «вы» не должен нигде увидеть «ты» (и наоборот).

Как разводить (что различается: местоимения ты/тебя/тебе/тобой, притяжательные
твой/…, глаголы 2 л. ед.ч., императивы `Отметь`→`Отметьте`):

- **Бот / уведомления** (бэкенд): `src/notification/address-form.ts` → `t(form, 'ты-текст', 'вы-текст')`.
  Тексты уведомлений уже полностью двухформенные, ориентируйся на них.
- **Фронтенды** (React): хук `useTr()` один раз в теле компонента → `const tr = useTr();`,
  затем `tr('ты-вариант', 'вы-вариант')`. Ещё есть `useAddressForm(): 'ty'|'vy'`,
  `useSetAddressForm()`, и чистый `pickForm(form, ty, vy)` для не-React мест.
  Инфраструктура — `schema-miniapp/src/utils/addressForm.tsx` и `webapp/src/utils/addressForm.tsx`.
- **Контент-файлы** (`needData.ts`, `aboutData.ts` и подобные `*Data.ts` с текстом):
  паттерн «билдер от формы» — `export const buildX = (tr) => (…)` где каждая различающаяся
  строка обёрнута в `tr('ты','вы')`, плюс хук-обёртка `useX() = getX(useAddressForm())`.
  Консьюмеры берут данные через `useX()`, а не импортируют константу напрямую.

Что **не** разводить (оставлять как есть):
- нейтральные/безличные/номинативные строки (названия, эмодзи, теги, 1-е лицо «я …»);
- дословные внутренние цитаты (`«…»`, `"…"`) — межличностная речь и самоподдержка,
  сохраняют свой регистр;
- сугубо клинические описания-убеждения, где «вы плохи» звучит нелепо — их лучше
  перефразировать **безлично** (form-agnostic), чем городить вилку.

**Согласование внутри «вы»-строки.** Мало заменить местоимение — вся фраза
обязана встать во множественное число: «вы дал» → «вы дали», «вы благодарен» →
«вы благодарны», «в чём вы вырос» → «в чём вы выросли». Свип 2026-07 нашёл 11
таких мест в `needData.ts` обоих фронтендов и в подсказках по схемам. Гейт —
`scripts/check-address-agreement.mjs` (CI, джоба `webapp`), без бейслайна.

**Строка с обращением обязана жить внутри `tr()`/`t()`/`pickForm()` — не
рядом, а внутри.** `check-address-form.mjs` выше ловит только жёсткие
«ты»-МЕСТОИМЕНИЯ во фронтендах. `scripts/check-second-person.mjs` (CI, джоба
`webapp`) закрывает то, что он не видел: захардкоженные императивы («Нажми»,
«Заполни») без единого местоимения рядом, зеркальные «вы»-формы (тот же баг,
только для «ты»-пользователя) и бэкенд (`src/` — письма, уведомления).
Родился из свипа 2026-08: блок `/account` в webapp, базовый `BottomSheet`
мини-аппа, три инфо-шторки и все письма показывали «ты» пользователю с формой
«вы» — инфраструктура форм существовала, её просто не вызвали. Пофайловый
храповик: `--update` фиксирует снижение, `--verbose` — что насчитано.

Проверка перед коммитом: прогнать по обоим `src` grep-свип на остаточные «ты»-формы
(`[Тт]ы`, `[Тт]еб[еяё]`, `[Тт]во[йяеё]`, окончания `ешь/аешь/ишь`), убедиться что
осталось только осознанно-нейтральное/цитаты. Лендинг/статьи/игра сайта — маркетинг,
не привязаны к `addressForm`, их не трогаем.

## Род читателя: мужских форм быть не должно (ОБЯЗАТЕЛЬНО)

Вторая ось к «ты/вы» — и до свипа 2026-08 она была не закрыта. Поля «пол» у
пользователя нет и заводить его не надо: род снимается формулировкой.

Форма «вы» защищена сама — множественное число рода не имеет («вы сделали»).
А «ты» стоит по умолчанию, и в ней род вылезает везде: **прошедшее время**
(«ты сделал», «ты вырос», «ты вернулся»), **краткие прилагательные** («ты не
обязан», «ты живой», «я рад», «я устал»), **творительный падеж** («позволь себе
быть сильным», «стать удобным», «оставаться спокойным»). Свип нашёл ~200 таких
мест — от пула канала до кнопки «Да, сделал ✓».

Как разводить (в порядке предпочтения — цель живой язык, а не обход правила):

1. **настоящее/будущее время**, у него рода нет: «ты перечитал своё сообщение
   третий раз» → «третий раз перечитываешь своё сообщение»;
2. **безличный оборот**: «когда ты справился» → «когда удалось справиться»;
   «Вчера ты планировал» → «Вчера в планах было»;
3. **существительное вместо прилагательного**: «позволь себе быть уязвимым» →
   «позволь себе немного уязвимости»; «быть компетентным» → «компетентность».

**Скобки «сделал(а)», «должен(на)» — не решение, а канцелярит.** Их гейт ловит
отдельно: живой текст так не пишут, читателя это спотыкает.

Что **не** трогать (там мужской род законный): он принадлежит другому слову
(«живой человек», «стабильный взрослый», «кто должен быть близким»), либо это
автор сайта о себе («приложение, которое я создал»).

Реплики от первого лица, которые пользователь **произносит или примеряет к
себе**, разводить обязательно — это его слова: «Скажи "я устал"» → «Скажи "сил
больше нет"»; «я плохой» → «со мной что-то не так».

Механизм принуждения: **`scripts/check-gendered-forms.mjs`** (CI, джоба
`backend`) — пофайловый храповик, новый файл рождается с нулём. Снизил —
зафиксируй: `--update`; посмотреть насчитанное: `--verbose`. Долг статей сайта
(`articles.seed.ts`) заморожен в бейслайне и обязан таять.

Свип 2026-08 закрыл четыре слепые зоны гейта, найденные ручной вычиткой 116
вопросов YSQ и карточек режимов (~50 пропущенных форм): узкий список глаголов
прошедшего времени (не видел «справился», «вырос», «устал» с опущенным
подлежащим); «сам»/«один» как незамечаемый маркер рода («Справлюсь сам»,
«останусь один») — раньше они гасились как filler, теперь ловятся как цель;
короткий список кратких прилагательных для «я» (был короче, чем для «ты»);
требование инфинитива вплотную к прилагательному — не ловило «чувствую себя
маленьким», «оказаться недостаточным». Паттерны и легитимные исключения
(`ALLOW`) вынесены в `scripts/gendered-forms-patterns.mjs` — движок гейта их
только импортирует (правило №10: движок не растёт вместе со списком правил).

## Онбординг и очевидность: «откуда это и зачем» (ОБЯЗАТЕЛЬНО)

Любая новая user-facing фича (трекер, дневник, тест, практика, экран) обязана
**до первого действия пользователя** ответить на два вопроса — и ответить
**в контексте**, на самом пути, а не в спрятанном «About»-оверлее, куда надо
ещё догадаться зайти:

1. **Откуда это** — что за сущность и на чём основана (напр. «пять базовых
   эмоциональных потребностей» из схема-терапии, а не безымянный «трекер»).
2. **Зачем это делать** — какой результат/паттерн получит пользователь и через
   какой срок (напр. «через 3–5 дней виден паттерн — что питает, что истощает»).

Правила:

- Объяснение живёт там, где пользователь **и так идёт** (шаг онбординга, первый
  экран фичи), а не только в отдельном разделе. Спрятанный контент = контента
  нет: если до смысла надо докопаться, для новичка его не существует.
- **Одно очевидное главное действие на экран.** Если непонятно «куда идти и что
  жамкать» — это баг дизайна, а не задача пользователя. Не вешай на один элемент
  несколько разных жестов (тап-открыть / драг-оценить / тап-разблокировать) без
  явных, различимых аффордансов и достаточных зон нажатия (цель ≥ 44×44).
- Переиспользуй уже выверенный объясняющий контент (`NEEDS_EXPLAINER`,
  `aboutData` и т.п.), а не пиши третью формулировку — тон и форма ты/вы там
  уже сведены (см. правило про «ты/вы»).

Механизм принуждения (ревью): проверяющий смотрит фичу глазами новичка и
спрашивает — «за 5 секунд понятно, что это, зачем и что нажать первым?». Нет —
фича не готова к мержу.

## Файлы

- Максимум ~150 строк на файл. Если больше — выноси в отдельный сервис.
- Не создавай новые файлы без необходимости. Один сервис = один файл.
- Не дублируй провайдеры: `PrismaModule` глобальный, не регистрируй `PrismaService` в других модулях.

## Одна механика — один компонент (НИКОГДА не реализуй одно и то же дважды)

**Одно и то же действие пользователя = один переиспользуемый компонент/хук.**
Если механика (оценить потребность, выбрать режим/схему, слайдер, список карточек)
встречается на нескольких экранах — она живёт в **одном** месте, а не копируется.
Копипаста взаимодействия — прямой источник рассинхрона: правку вносят в одну копию,
вторая тихо остаётся старой (реальный инцидент: оценка потребности была слайдером
и в `NeedSlider`, и в `NeedTodaySheet`; перевели на тап только первую — экраны
разъехались. Итог: общий контрол `NeedRatingBar`, оба экрана берут его).

Второй реальный случай (свип 2026-08): механика «пара с другом» (загрузка,
создание/приём приглашения, отвязка) была написана дважды — независимо в
`PairSheet.tsx` и в `SettingsSheet.tsx`/`PartnerSection.tsx`. Копии разошлись
**поведением**, не только текстом: в настройках отвязка партнёра уходила без
подтверждения, а ошибка приглашения глоталась молча. Свели в общий хук
`usePairMechanics` + `PairPanel` (`schema-miniapp/src/components/pairSheet/`) —
обе поверхности берут одну логику, своя у каждой остаётся только разметка.

**Перед тем как писать новый контрол/слайдер/список/парсер — обязательно `grep`:**
уже есть похожее? Есть — переиспользуй или вынеси общий примитив (компонент/хук/util).
Нет — пиши один раз так, чтобы переиспользовать, а не «пока быстренько сюда скопирую».

Красные флаги на ревью (любой = фича не готова):
- две реализации одного ввода (`onPointerDown`/`calcValue`/`trackRef`/одинаковый JSX
  в разных файлах);
- «поправил в одном месте — в другом осталось по-старому»;
- новый компонент, дублирующий уже существующий по смыслу, вместо переиспользования.

Механизм принуждения: перед добавлением интерактивного элемента — поиск существующего;
при дубле — вынос в общий модуль **в том же PR**. Ревьюер спрашивает: «это уже
где-то реализовано? почему не переиспользовано?». Для дублей между фронтендами —
см. правило №3 (парные файлы / shared-пакет).

## Никаких хардкод-заглушек вместо реальных данных (НИКОГДА)

**Данные, которые пользователь видит как свои (оценки, история, «вчера»,
статистика), берутся ТОЛЬКО из реального источника (API/БД/локальное
хранилище) — никогда из захардкоженной константы.** Заглушка-фолбэк —
прямой обман: на чистом аккаунте показываются чужие/выдуманные цифры, и это
читается как «данные не удалились» (реальный инцидент: константа `YESTERDAY`
`{expression: 4, …}` подставлялась как «вчера», когда реальных данных нет).

Правила:

- Нет реальных данных → показывай **пусто/скелетон/«—»**, а не выдуманное
  число. `real ?? HARDCODED_FALLBACK` для пользовательских данных запрещён.
- Демо/сид-данные не живут в рантайм-коде фронта. Нужен демо-режим — явный
  флаг и явная пометка «пример», не молчаливый фолбэк.
- Что **можно** (это не заглушки данных): `placeholder=""` в полях ввода;
  нейтральный **дефолт-старт** редактируемого контрола (слайдер с середины),
  который пользователь тут же меняет и который не выдаётся за сохранённое.

Механизм принуждения (ревью): «эта цифра/строка — из реальных данных
пользователя? что покажется на чистом аккаунте?». Захардкоженное значение,
которое юзер примет за своё, — фича не готова.

## Загрузка: скелетоны по форме контента, а не спиннеры (ОБЯЗАТЕЛЬНО)

**Пока грузятся данные — показывай плейсхолдер ПО ФОРМЕ будущего контента,
а не крутилку/котика и не пустоту.** Скелетон, повторяющий силуэт экрана
(шапка, карточки, строки списка), убирает сенсорный скачок при появлении
данных (нейроинклюзивность, ADHD/аутизм) и даёт ощущение, что экран уже
«на месте», а не «висит».

Правила:

- Единый примитив — `schema-miniapp/src/components/Skeleton.tsx`: `Skeleton`
  (плашка), `SkeletonCard`, `SkeletonLines`, `SkeletonList`, плюс силуэты
  экранов (`TodayScreenSkeleton`, `ScreenSkeleton`). Не пиши новый шиммер
  инлайном — переиспользуй/дополни примитив (правило «одна механика — один
  компонент»).
- **Форма скелетона совпадает с контентом.** Список практик → `SkeletonList`
  из карточек той же высоты; экран с крупной CTA → большой rounded-блок;
  текст → `SkeletonLines`. Три одинаковых серых прямоугольника на месте
  сложного экрана — это «не та форма», чини.
- Спиннер/«Загрузка…»-текст допустим только для мгновенных действий-кнопок
  (сохранение, отправка), не для загрузки экрана или списка.
- Шиммер уже глушится reduced-motion блоком `index.css` — отдельно
  отключать не нужно.

Механизм принуждения (ревью): «что видно в первую секунду загрузки? силуэт
будущего экрана или крутилка/пустой прямоугольник?». Спиннер вместо
скелетона или скелетон не по форме — фича не готова.

## Никакого размытия во фронтендах (по итогам расследования 2026-08-26)

`backdrop-filter` и `filter: blur(...)` запрещены. Не «нежелательны» —
запрещены гейтом `scripts/check-render-poison.mjs`.

Неделю мини-апп «первую минуту ужасно тормозил» из ярлыка на телефоне и при
этом летал в Telegram. Перебрали и отвергли: service worker (#426), объём
стартовой работы (#424/#425), скорость движка (бенчмарк в приложении — 7-14мс,
JIT работает). Ответ дала панель замеров на устройстве владельца: кадры и
таймеры замирали **ровно раз в ~1.5с** — метроном, а не работа. Выключение
одного только размытия (тумблер `noblur`, `perfExperiments.ts`) убрало всё
разом: 42 блока и 78с зависаний → 0, тап 2000-4000мс → 115-196мс.

Механика: в установленном на телефон приложении (standalone PWA) WebKit
считает размытие программно, без ускорения, которое тот же код получает
внутри Telegram. Полноэкранный `blur(90px)` и пересэмплирование фона под
нижней панелью стоили ~1.4с **на кадр**, и в этой же очереди стояли касания
пальца — отсюда «жму, а экран меняется через секунду-полторы».

Что из этого следует:

- **Вместо стекла — сплошной цвет.** `--nav-bg` равен цвету фона, панель
  выглядит ровно так же, как выглядела сквозь размытие фона того же цвета.
  Полупрозрачная подложка без блюра запрещена отдельно: она даёт чёткое
  просвечивание текста, ту самую «кашу», из-за которой альфу уже поднимали.
- **Декор, которого не видно, всё равно стоит кадров.** `AmbientBackground`
  мини-аппа рисовал два полноэкранных круга с `blur(90px)` цветом
  `rgba(0,0,0,0)` — невидимые, но пересчитываемые каждый кадр. Прозрачный или
  выключенный токеном эффект не бесплатен: удаляй элемент, а не цвет.
- **Дорогое свойство на анимируемом элементе — худшая пара.** Блюр под тем,
  что бесконечно едет (`animation: … infinite`), переразмывает задний план
  на каждом кадре.
- **Мягкое свечение рисуется градиентом**, а не размытым кругом:
  `radial-gradient` растеризуется один раз.

Механизм принуждения: `scripts/check-render-poison.mjs` (CI, джоба `webapp`)
— пофайловый храповик. Значение `none` и комментарии не считаются (иначе
гейт красил бы собственный инструмент замеров и пояснения в коде). Долг
маркетинговых лендингов сайта заморожен в бейслайне и обязан таять, новый
файл рождается с нулём.

Отладка скорости на устройстве: панель `PerfHud` включается пятью тапами по
строке версии в «О приложении» (`BuildInfoLine`), показывает очередь тапа,
блоки главного потока, паузы таймеров и метки старта; тумблеры `noanim`/
`noblur` ставят A/B прямо на телефоне. **Так и надо искать причину — по
цифрам с устройства, а не перебором гипотез:** неделя перебора не дала
ничего, один замер дал ответ.

## Тесты (ОБЯЗАТЕЛЬНО для новой логики)

**Любой новый код с логикой обязан приезжать с тестом.** Не «когда-нибудь потом» —
в том же коммите. Тесты — `*.spec.ts` рядом с кодом (`npx jest`), сервис
инстанцируется напрямую с замоканной/поддельной Prisma (примеры:
`bot.analytics.service.spec.ts`, `notes.service.spec.ts`).

**Особый случай — read-after-write.** Если фича *пишет* состояние в одном месте,
а *читает/показывает* его в другом — тестируй **связку сохранение→отображение**,
а не только запись. Тест на «сохранилось ли» проходит зелёным даже когда карточку
потом «не найти». Реальные баги живут именно на стыке: пиши тест «сохранил → нашёл».

Триггеры, при которых read-after-write тест обязателен:
- есть **денормализованное/дублированное состояние**, которое должно совпадать
  (напр. `mySchemaIds`/`myModeIds` ↔ наличие `UserSchemaNote`/`UserModeNote`;
  sequence ↔ реальный `max(id)`) — тестируй, что оно не разъезжается;
- у сохранения есть **побочный инвариант** (заполнил карточку ⇒ она в коллекции);
  инвариант держи в сервисе (нижний слой), а не в UI-кнопке — и тестом фиксируй;
- у одного действия **несколько точек входа** (упражнение открывается из 5 мест) —
  тест бьёт по сервису, чтобы ни один клиент не мог сохранить мимо инварианта.

Каждый пойманный на проде баг → регрессионный тест, воспроизводящий сценарий
(комментарий-ссылка на инцидент сверху файла, как в `notes.service.spec.ts`).

## Тестовые храповики и e2e (по итогам покрытия 2026-07-16)

- **Coverage-храповик**: `scripts/check-coverage-ratchet.mjs` (CI-джоба
  backend) — покрытие бэкенда не может снизиться; полы по каталогам в
  `scripts/coverage-baseline.json`. Стало лучше — зафиксируй `--update`.
- **Новый контроллер/эндпоинт = e2e-смок на ownership**: тест в `test/`,
  что юзер А не видит данные юзера Б через HTTP (см. `app-ownership.e2e-spec.ts`;
  инфраструктура — `test/e2e-support/`, бут реального AppModule).
- **Инварианты telegram-хендлеров** держит `telegram.invariants.spec.ts`
  (try/catch, `answerCbQuery` до БД, запрет console.log) — allowlist в нём
  пуст и может только сокращаться.
- **Новый гейт приезжает со своим тестом** (`src/test-support/gates/`).
  Сломанный гейт не краснеет — он молча пропускает всё, и защита живёт
  только на бумаге. Тест запускает скрипт в песочнице (копия скрипта +
  фикстуры во временном каталоге, вызов как в CI) и проверяет ОБА исхода:
  краснеет на регрессе и зеленеет на чистом дереве. Второй не менее важен:
  ложно-красный гейт отключают через неделю. Образец — `gate-sandbox.ts`.
  Гейт, доросший до лимита размера (правило №10), дробится на движок +
  модуль правил — песочница копирует скрипт вместе с его локальными
  `from './*.mjs'`-зависимостями, иначе раздробленный гейт падал бы в тесте
  с `ERR_MODULE_NOT_FOUND`.
- **Ключевые e2e гоняются дважды**: на фейковой Prisma и на живом Postgres
  (джоба `migrations`, `E2E_REAL_DB=1`). Фейк трижды расходился с реальной
  БД при зелёных тестах; всё, что про фильтрацию по `userId`, уникальные
  констрейнты и транзакции, обязано пройти по живой базе.

## Обработка ошибок

- **Все** Telegram-хендлеры (команды и action) обёрнуты в `try/catch`.
- `answerCbQuery()` вызывается **до** обращения к БД или внешним сервисам — иначе Telegram покажет вечный спиннер.
- Если `editMessageText` / `reply` могут упасть внутри catch, добавляй `.catch(() => null)`.
- Ошибки логируются через `this.logger.error(...)`, не через `console.log`.

## Безопасность

> Полный security-плейбук — модель угроз, инварианты аутентификации/авторизации,
> анти-паттерны, чеклист перед деплоем, реагирование на инциденты — в [docs/SECURITY.md](docs/SECURITY.md).
> Читать перед изменением auth/api/therapy-кода.

- Все env-переменные читаются через `ConfigService` или `process.env` — не хардкодить значения.
- Данные из callback_data (needId, value) всегда валидируются перед использованием.
- Команды с побочными эффектами (например `/post`) защищены проверкой `ADMIN_ID`.

### Критичные env-переменные
- `BOT_TOKEN` — токен бота. При компрометации: revoke в BotFather → новый токен → инвалидирует ВСЕ initData (юзеры в мини-аппе будут разлогинены, пройдут заново)
- `JWT_SECRET` — подпись access/refresh/merge токенов. При компрометации: ротация → все сессии (web) инвалидируются, merge-токены становятся бесполезны. Юзерам надо залогиниться заново.
- `ENCRYPTION_KEY` — шифрует свободный текст (заметки, дневники, письма, безопасное место). **Никогда не ротируй без re-encryption миграции** — иначе все зашифрованные данные превратятся в мусор. План ротации:
  1. Добавить второй ключ `ENCRYPTION_KEY_NEW`
  2. При чтении пробовать оба ключа (decryptRecord fallback)
  3. Прогнать скрипт: расшифровать всё старым ключом, зашифровать новым, переписать в БД
  4. Удалить старый ключ
- `GOOGLE_CLIENT_SECRET` — клиентский секрет для OAuth. Ротация в Google Cloud Console + обновление env.
- `ADMIN_ID` — Telegram ID единственного администратора. Все админские callback'и проверяют по нему.
- `HEALTHY_ADULT_MAX_CA` — необязательное перекрытие корневого сертификата для
  запросов в MAX. По умолчанию корень берётся из репозитория
  (`assets/ca/russian-trusted-root.pem`, публичный сертификат госуслуг) и
  доверяется **только** запросам к площадке — глобальный `NODE_EXTRA_CA_CERTS`
  здесь запрещён: он расширил бы доверие на Telegram, Google и БД.
- `HEALTHY_ADULT_MAX_TOKEN` — токен бота MAX. Одна и та же строка работает на
  две вещи, потому что бот один: он публикует в канал «Здоровый Взрослый»
  (`src/channel/targets/max.target.ts`) **и** им же подписан initData мини-аппа
  (`src/auth/max-init-data.ts`). Подпись считается по токену того бота, под
  которым зарегистрировано мини-приложение (запуск идёт по ссылке
  `https://max.ru/<botName>?startapp=…`) — это правило площадки, а не наш выбор.

  Отсюда важное: **вес этого секрета больше, чем кажется по имени**. Утечка
  даёт не «чужой запостит в канал», а возможность подделать подпись и войти
  **под любым пользователем MAX**. Ротация тоже бьёт по двум местам сразу:
  канал продолжит работать только с новым значением, а все выданные
  MAX-подписи станут недействительны — пользователи мини-аппа переоткроют его
  и войдут заново.

- `MAX_BOT_TOKEN` — **необязательное** перекрытие предыдущей переменной, на
  случай если мини-апп переедет под отдельного бота. Задана — сильнее
  канальной; не задана — берётся канальная. Второй копии того же секрета
  заводить не надо: две переменные с одним значением обязывают ротировать их
  синхронно, а забытая половина ломает молча — либо канал перестаёт постить,
  либо все входы начинают падать.

  Пока не задана ни одна из двух, вход из MAX отвечает 503 «не настроено» и
  **не** шлёт алерт о подделке (`MaxNotConfiguredError`) — остальные площадки
  работают как работали.

  Отладка: если входы из MAX массово отдают 401, первым делом сверь, что токен
  принадлежит именно тому боту, под которым открыто мини-приложение. Неверный
  токен криптографически неотличим от подделки — в аудит-логе это выглядит
  как атака.

### Аудит-события
`SecurityLogService` пишет в логи + DM админу при: merge_confirmed, role_changed, therapist_request_submitted, csrf_blocked, suspicious_initdata (попытка подделать подпись). Если приходит много suspicious_initdata — атака или ротация BOT_TOKEN не докатилась.

### Резервные копии БД (важно для шифрования при компрометации)
Поля в БД зашифрованы AES-256-GCM с ключом из env `ENCRYPTION_KEY`. **Если утечёт бэкап Amvera CNPG + env-snapshot одновременно — данные открыты**.

Что нужно от Amvera (запросить у их саппорта):
1. Шифруются ли резервные копии CNPG at-rest?
2. Где они хранятся (в том же ДЦ, отдельно, у третьей стороны)?
3. Кто имеет к ним доступ (только владелец проекта или сотрудники Amvera)?
4. Encryption keys для бэкапов — ваши или Amvera управляет?

Долгосрочные меры (если хочется паранойи):
- ENCRYPTION_KEY держать **не в env**, а в отдельном secret manager / HSM (для Amvera маловероятно).
- Делать собственные офлайн encrypted dumps (`pg_dump | openssl enc -aes-256-gcm`) и хранить в другом облаке.
- Принять что для российского небольшого хостинга это accepted risk.

### Ротация ENCRYPTION_KEY
1. Сгенерить новый ключ: `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`
2. В Amvera env: `ENCRYPTION_KEY_OLD = <старый>`, `ENCRYPTION_KEY = <новый>`. Restart.
3. Запустить `npm run rotate-encryption` (через Amvera exec/SSH).
4. Убрать `ENCRYPTION_KEY_OLD`. Restart.

`decrypt()` поддерживает несколько ключей одновременно — старые читаются как fallback, новые записываются всегда current ключом.

### Удаление аккаунта
`deleteAllUserData` теперь **hard delete** (не soft с deletedAt-флагом):
- DELETE по всем USER_DATA_TABLES + AuthProvider + WebSession + TherapistRequest + сам User
- После транзакции триггер `VACUUM ANALYZE` (не FULL, не блокирует) → быстрее освобождает dead tuples
- Юзер удалён логически мгновенно. Физическое освобождение страниц Postgres'ом — через autovacuum в течение часов.

Для строгого GDPR-уровня right-to-erasure нужен ещё `VACUUM FULL` (лочит таблицы) или disk-level encryption. Не делаем, accepted risk.

## Новый fullscreen-лист или оверлей в webapp (ОБЯЗАТЕЛЬНО)

Любой компонент с `position: fixed, inset: 0` (sheet, экран упражнения, оверлей) **обязан** использовать хук `useHistorySheet` — иначе кнопка «Назад» в браузере уведёт пользователя из приложения.

```tsx
import { useHistorySheet } from '../hooks/useHistorySheet'; // путь от компонента

export function MySheet({ onClose }: { onClose: () => void }) {
  const goBack = useHistorySheet(onClose);
  // ...
  return (
    <div style={{ position: 'fixed', inset: 0, zIndex: 90, ... }}>
      <button onClick={goBack}>Назад</button>   {/* НЕ onClick={onClose} */}
    </div>
  );
}
```

Правила:
- Хук вызывается **один раз** в теле компонента, принимает функцию закрытия (`onClose` / `onBack` / `onDone`).
- Все кнопки «Назад» и «Закрыть» внутри листа используют `goBack()`, **не** `onClose()` напрямую.
- Если лист закрывается после сохранения (`await api.save(); goBack()`), тоже `goBack()`.
- Исключение: внутренние мини-модалки поверх листа (тёмный backdrop для подтверждения) — у них свой локальный `onClose`, хук там не нужен.

**Важно — не использовать `history.pushState` или `window.addEventListener('popstate')` напрямую.**
Хук работает через `useNavigate`/`useLocation` из react-router-dom. Прямой вызов `history.pushState` конфликтует с React Router: при нажатии «Назад» срабатывают оба обработчика одновременно — лист закрывается И роутер уходит на предыдущий раздел.

## Деплой webapp

`webapp/dist/` **не хранится в git** — Amvera сама собирает webapp из исходников через
`RUN npm run build --prefix webapp` в `Dockerfile`.

**Деплой = push в GitHub (`origin/main`). Amvera сама тянет из GitHub и пересобирает** —
отдельный `git push amvera` НЕ нужен. Просто `git push origin main`.

### Мини-апп (`schema-miniapp/`) — важно
Собирается **НЕ** в Docker, а заранее: его `dist/` **коммитится в git**, а Dockerfile
только копирует его в `webapp/dist/app/` (быстрая сборка, без лишнего install/build).
Исходник мини-аппа тоже в git. При изменении исходника мини-аппа:

```bash
npm run build --prefix schema-miniapp   # пересобрать dist
git add schema-miniapp/dist && git commit ...   # закоммитить dist
```

`.dockerignore` исключает исходник мини-аппа из Docker-контекста — поэтому собрать его
в Docker нельзя, только копировать готовую `dist`. Не переключай Dockerfile на сборку
мини-аппа — билд упадёт («Could not resolve entry module index.html»).

Локальная сборка webapp для проверки ошибок TypeScript/Vite:

```bash
cd webapp && node_modules/.bin/vite build
```

## Миграции БД (ОБЯЗАТЕЛЬНО — по итогам инцидента 2026-07-16)

Инцидент: рукописная миграция с сидом (`healthy_adult_phrases`) не заполняла
`updatedAt NOT NULL` → упала на проде при `migrate deploy` → P3009 заблокировал
все миграции → **крашлуп прода на несколько часов**. Ни один существующий чек
(tsc, jest, eslint) SQL не исполняет — битая миграция была невидима до прода.

Правила:

1. **SQL миграции обязан быть исполнен до коммита.** Генерируй через
   `prisma migrate dev` (он сразу применяет к dev-БД). Рукописный/правленый
   SQL — прогони `migrate deploy` на чистой локальной БД. «Выглядит валидно»
   — не проверка: инцидентный SQL был синтаксически корректен.
2. **Ловушка Prisma `@updatedAt`**: колонка в БД — `NOT NULL` **без DEFAULT**
   (значение ставит клиент, не Postgres). Любой сырой `INSERT` в миграции/сиде
   обязан явно заполнять `updatedAt` (`CURRENT_TIMESTAMP`). То же для всех
   NOT NULL-колонок без дефолта.
3. **Сид в миграции — идемпотентный**: `CREATE TABLE IF NOT EXISTS`, вставка
   через `WHERE NOT EXISTS` — чтобы повторный прогон после падения/отката был
   безопасен.
4. **Диагностика падения миграции — с ПЕРВОЙ ошибки.** P3009/P3018 — симптом,
   не причина. Ищи в логах первое падение (по времени из "started at ...") и
   его SQLSTATE — иначе чинишь следствие, а не корень (в инциденте так потеряли
   несколько итераций).
5. Восстановление на Amvera без внешнего доступа к БД: одноразовый
   `prisma db execute --file <recover>.sql` в CMD перед `migrate deploy`
   (см. `prisma/recover-p3009.sql`; в Prisma 7 у `db execute` **нет** флага
   `--schema` — URL берётся из `prisma.config.js`). После стабилизации —
   убрать из CMD.

Механизм принуждения: CI-джоба **`migrations`** — поднимает Postgres 16 и
гоняет `prisma migrate deploy` на пустой БД (дважды). Битый SQL роняет PR,
а не прод.

## Новая таблица с пользовательскими данными — обязательный чеклист

При добавлении любой модели с полем `userId` **обязательно** выполнить все 4 шага:

**1. Удаление при удалении аккаунта И перенос при merge**
Добавить имя модели в **оба** реестра:
- `USER_DATA_TABLES` в начале `src/bot/bot.service.ts` — `deleteAllUserData` очистит её;
- `USER_OWNED_TABLES` в `src/auth/merge.service.ts` (+ правило в `UNIQUE_RULES`,
  если у модели есть unique-констрейнт с userId) — иначе при merge аккаунтов
  данные останутся на старом userId и потеряются для пользователя.
TypeScript проверит имена (`_VerifyTables`), а spec-сверка со schema.prisma
(план: этап 1.1 docs/archive/REMEDIATION_PLAN.md) упадёт, если модель забыта в одном из списков.

**2. Шифрование**
Объявить `EncryptSchema` рядом с методами модели:
```typescript
const MY_SCHEMA: EncryptSchema = { strings: ['text', 'note'], jsonArrays: ['items'] };
```
Использовать `encryptRecord(data, MY_SCHEMA)` при записи и `decryptRecord(row, MY_SCHEMA)` при чтении.
Не шифровать: `id`, `userId`, `createdAt`, `updatedAt`, типы-перечисления (modeId, schemaId, needId).

Механизм принуждения: `src/utils/encryption-coverage.spec.ts` — реестр решений
о шифровании для КАЖДОГО String/Json-поля каждой модели. Новое поле без записи
в реестре роняет jest в CI; `enc`-запись проверяется по исходнику сервиса,
`plain`-запись требует причину. Молча добавить plaintext-колонку со свободным
текстом невозможно (найдено аудитом 2026-07-20: черновики дневников, ответы
YSQ, заявки терапевтов, алиасы клиентов и email в magic-link токенах лежали
в открытом виде).

**3. Каскадное удаление в Prisma**
```prisma
user  User  @relation(fields: [userId], references: [id], onDelete: Cascade)
```

**4. После изменений схемы**
```bash
npx prisma generate
```
