# Данные: Prisma, миграции, сырой SQL, планы запросов

> Схема БД, миграции, новые таблицы с userId, денормализация, сырой SQL и замер планов. Полный текст правил: файл подгружается сам, когда агент читает или правит
> файлы из `paths` выше. Краткая строка каждого правила — в [CLAUDE.md](../../CLAUDE.md);
> номера (№N) общие с CLAUDE.md и с комментариями в коде.

## 4. Денормализация и дублированные реестры — только с тестом-сверкой
Любые два места, обязанные совпадать (`USER_DATA_TABLES` ↔ `USER_OWNED_TABLES`
↔ schema.prisma; `mySchemaIds` ↔ `UserSchemaNote`), фиксируются тестом,
который падает при рассинхроне. Read-modify-write по денормализованному
полю — только в `$transaction` или через пересчёт из источника правды.

## 18. Сырой SQL исполняется на живом Postgres, мок его не проверяет (инцидент 2026-09-13)

<!--
Запись на консультацию падала 500 на **каждой** попытке: `pg_advisory_xact_lock`
возвращает `void`, а Prisma 7 с driver-adapter не умеет прочитать такую колонку
в `$queryRaw`. Двенадцать юнит-спеков бронирования были зелёными — все они
мокали `$queryRaw` заглушкой «вызвали, вернулось ничего». Мок отвечает что
угодно; умеет ли **драйвер** прочитать ответ на этот запрос — свойство
Postgres и Prisma, а не нашего кода, и доказывается только настоящей базой.
Тот же класс, что у фейковой Prisma (правило «ключевые e2e гоняются дважды»):
фейк трижды расходился с реальностью, и каждый раз чинили один спек, а не
класс. К моменту инцидента из 31 файла с сырым SQL на живой базе гонялись 6;
весь отчёт `/stats` (20 сервисов) жил только на моках.
-->

Механизм:

- **`test/raw-sql-live-*.e2e-spec.ts`** (джоба `migrations`) исполняют каждое
  место с сырым SQL на живом Postgres: весь `/stats` дважды — на базе как есть
  (пустое состояние, правило №8: без «NaN/undefined») и после фикстур, чтобы
  ветки группировки по `meta` прошли через драйвер; `/health`, зонд аварии
  БД, VACUUM после удаления аккаунта, захват списания подписки.
- **`scripts/check-raw-sql-live.mjs`** (CI, джоба `checks`) требует
  **классификации** каждого файла `src/**` с `$queryRaw`/`$executeRaw`/
  `…Unsafe`/`Prisma.sql` в `scripts/raw-sql-live-baseline.json`: `{spec}` —
  спек импортирует файл (или через одну ступень `via`) и стоит в джобе
  `migrations`; либо `{exempt, since}` с честной причиной. Флага `--update`
  нет намеренно — как у гейта кронов: гейт, ищущий признак, молчит о том,
  чего не знает. Протухшая запись роняет CI.

Что из этого следует для работы:

- **Новый сырой запрос приезжает со строкой в живом спеке и записью в
  бейслайне в том же PR.** Юнит с моком `$queryRaw` — не проверка запроса,
  а проверка того, что метод его вызвал.
- **Функция, возвращающая `void`, берётся через `$executeRaw`**, который
  колонки ответа не читает (`booking-slot-lock.ts`). `$queryRaw` — только
  для запросов с типизированными колонками.
- **Резерв для денег и заявок.** Падение создания брони теперь уходит админу
  лидом (имя, контакт, слот) сразу в Telegram **и** на почту
  (`BookingNotifyService.notifyAdminBoth` в `src/booking/booking-notify.service.ts`,
  зовётся из `booking.create.ts`) — по образцу донатов. Клиент
  видит честный текст «заявка не сохранилась», а не «время заняли, обновите
  страницу» (`BookingErrorNote.tsx`), и сбой уходит наверх секцией `booking`.

## 28. План запроса доказывается замером, а не чтением схемы (2026-10-08)

> Сам замер — цифры, планы, решения по каждой находке — в
> [docs/PERF_PLANS.md](../../docs/PERF_PLANS.md).

<!--
Производительность была единственной зоной, которую аудиты проверяли **чтением
схемы**: `archive/PROJECT_AUDIT_ADDENDUM.md` §3 (D-4: «первый кандидат в узкое
место») и `security/AUDIT_2026-08-12.md` (M2/M3/H3/H4). Индекс `Rating.date` по
находке M2 добавили по рассуждению — и замер показал, что одной колонки мало:
индекс находил строки, а `userId` всё равно читался из таблицы. Рассуждение про
план — гипотеза; план отдаёт только `EXPLAIN`.
-->

Механизм — джоба `perf` в `ci.yml`: сидер синтетики (`test/perf/seed.ts`),
прогон горячих путей **реальными сервисами** (`test/perf/scenarios.ts`),
EXPLAIN с записанного SQL (`test/perf/run-plans.ts`) и гейт
`scripts/check-query-plans.mjs` (планки — `scripts/query-plan-baseline.json`,
тест гейта — `src/test-support/gates/query-plans.spec.ts`).

Что из этого следует для работы:

- **Новый горячий путь = сценарий в `test/perf/scenarios.ts`.** Сценарий — это
  вызов сервиса, а не SQL-строка: что уйдёт в базу, решает код прода, и
  записывается это на уровне драйвера (`pg.Client.query`). Поэтому новый запрос
  внутри уже измеряемого пути попадает под гейт сам, без того чтобы кто-то
  вспомнил его зарегистрировать. **Запрос, переписанный в файл замера руками,
  расходится с кодом молча** — тот же класс, что мок `$queryRaw` (правило №18)
  и сочинённая автором фикстура (правило №23).
- **Гейт краснеет не на «есть Seq Scan».** Seq Scan законен: запрос без WHERE
  (`count(DISTINCT "userId") FROM "UserPractice"`) читает таблицу целиком, и
  индекс ему не поможет — гейт, краснеющий на таком плане, учил бы себя
  обходить (правило №15). Диагноз — **прочитал много, отдал мало** (≥90%
  выброшено фильтром) и **повторный полный проход** (loops > 1).
- **Планка — в страницах, а не в миллисекундах.** Страницы детерминированы при
  фиксированной синтетике; время на раннере скачет в разы, и гейт по времени
  отключили бы через неделю как ложно-красный. Время остаётся грубым потолком
  (`msCeiling`) и ставится руками: `--update` его не придумывает.
- **Сидер обязан делать `VACUUM (ANALYZE)`, не только `ANALYZE`.** Без карты
  видимости Index Only Scan деградирует в heap fetches, и замер мерит артефакт
  сидера, а не прод: один и тот же запрос дал 3 016 179 страниц против 5 559
  после VACUUM. Данные сидера детерминированы (никакого `random()`) — иначе
  планка по страницам шумела бы от прогона к прогону.
- **Объём синтетики — горизонт роста, а не ×10 от сегодняшних цифр.** На
  двух тысячах строк Postgres законно выбирает Seq Scan, и гейт краснел бы на
  правильных планах. Профиль — `test/perf/seed-profile.ts`, причина выбора — в
  `docs/PERF_PLANS.md`.
- **Новый индекс — обычный `CREATE INDEX`, не `CONCURRENTLY`**: внутри
  транзакции миграции CONCURRENTLY не работает, а падение такого шага оставляет
  инвалидный индекс и P3009, то есть крашлуп прода (правило о миграциях).
  Индекс по тем же ведущим колонкам **заменяется, а не добавляется**: третий
  индекс на самой растущей таблице — лишняя запись на каждый INSERT.

### Чего гейт планов не видит

Честно, чтобы следующий не считал зону закрытой целиком: гейт смотрит только
**читающие** запросы (EXPLAIN ANALYZE исполняет запрос, и для INSERT/UPDATE это
означало бы правку данных замера), один процесс без конкуренции и синтетику, а
не прод. Блокировки, раздувание таблиц и живой размер прода — за кадром.

## БД

- Схема: `prisma/schema.prisma`. После изменений — `prisma migrate dev --name <название>`.
- В проде миграции применяет контейнер сам: CMD в `Dockerfile` —
  `node deploy/entrypoint.mjs`, он зовёт `migrate deploy` до старта приложения
  (`start:prod` из package.json контейнер не запускает).
- **Дампы и бэкапы БД никогда не кладутся в репозиторий** — он публичный.
  Бэкапы — только через `scripts/backup-upload.sh` во внешнее хранилище (Cloudflare R2).
- **Предел запроса — 30 с на каждый запрос** (`statement_timeout` сессии пула,
  `src/prisma/statement-timeout.ts`; порог согласован владельцем 2026-10-22,
  аудит 2026-10). Долгий легитимный путь берёт `withStatementTimeout(prisma, мс,
  tx => …)` — `SET LOCAL` в своей транзакции, в пул не протекает, — а не поднимает
  общий порог; отдельный процесс со своим `PrismaClient` — `buildPrismaAdapter(порог)`
  (ротация ключа — 10 мин). Миграции ходят своим подключением по `DATABASE_URL` и
  лимита не получают — поэтому порог не кладётся в URL. Доказательство на живой
  базе — `test/statement-timeout.e2e-spec.ts` и `test/perf/long-paths.ts`.

## Миграции БД (ОБЯЗАТЕЛЬНО — по итогам инцидента 2026-07-16)

<!--
Инцидент: рукописная миграция с сидом (`healthy_adult_phrases`) не заполняла
`updatedAt NOT NULL` → упала на проде при `migrate deploy` → P3009 заблокировал
все миграции → **крашлуп прода на несколько часов**. Ни один существующий чек
(tsc, jest, eslint) SQL не исполняет — битая миграция была невидима до прода.
-->

Правила:

1. **SQL миграции обязан быть исполнен до коммита.** Генерируй через
   `prisma migrate dev` (он сразу применяет к dev-БД). Рукописный/правленый
   SQL — прогони `migrate deploy` на чистой локальной БД. «Выглядит валидно»
   — не проверка: инцидентный SQL был синтаксически корректен.
2. **Ловушка Prisma `@updatedAt`**: колонка в БД — `NOT NULL` **без DEFAULT**
   (значение ставит клиент, не Postgres). Любой сырой `INSERT` в миграции/сиде
   обязан явно заполнять `updatedAt` (`CURRENT_TIMESTAMP`). То же для всех
   NOT NULL-колонок без дефолта.
3. **Миграция идемпотентна целиком, не только сид**: `CREATE TABLE IF NOT EXISTS`,
   вставка через `WHERE NOT EXISTS`, `UPDATE`, дающий тот же результат при
   повторе. Это не рекомендация: Prisma не оборачивает миграцию в транзакцию, а
   `prisma/recover-p3009.sql` при каждом старте контейнера снимает застрявшую
   запись, то есть миграция, упавшая посередине, применяется заново на каждом
   рестарте — неидемпотентный оператор до места падения повторится.
4. **Диагностика падения миграции — с ПЕРВОЙ ошибки.** P3009/P3018 — симптом,
   не причина. Ищи в логах первое падение (по времени из "started at ...") и
   его SQLSTATE — иначе чинишь следствие, а не корень (в инциденте так потеряли
   несколько итераций).
5. Восстановление без внешнего доступа к БД: `deploy/entrypoint.mjs` перед
   `migrate deploy` всегда исполняет `prisma/recover-p3009.sql` (`RECOVER_CMD`) —
   он снимает ЛЮБУЮ застрявшую запись (`finished_at IS NULL`), кроме миграции,
   которая выполняется прямо сейчас (замок Prisma занят). На VPS то же делает
   автооткат и ручной `op=migrate-resolve-failed`. В Prisma 7 у `db execute`
   **нет** флага `--schema` — URL берётся из `prisma.config.js`.

Механизм принуждения: CI-джоба **`migrations`** — поднимает Postgres 16 и
гоняет `prisma migrate deploy` на пустой БД (дважды). Битый SQL роняет PR,
а не прод.

## Новая таблица с пользовательскими данными — обязательный чеклист

При добавлении любой модели с полем `userId` **обязательно** выполнить все 4 шага:

**1. Удаление при удалении аккаунта И перенос при merge**
Добавить имя модели в **оба** реестра:
- `USER_DATA_TABLES` в `src/bot/user-data-tables.ts` — `deleteAllUserData` очистит её;
- `USER_OWNED_TABLES` в `src/auth/user-owned-tables.ts` (+ правило в `UNIQUE_RULES` в `src/auth/merge.service.ts`,
  если у модели есть unique-констрейнт с userId) — иначе при merge аккаунтов
  данные останутся на старом userId и потеряются для пользователя.
TypeScript проверит имена (`_VerifyTables`), а spec-сверка со schema.prisma
(`src/auth/table-registry.spec.ts`) упадёт, если модель забыта в одном из списков.

**2. Шифрование**
Объявить `EncryptSchema` рядом с методами модели:
```typescript
const MY_SCHEMA: EncryptSchema = { strings: ['text', 'note'], jsonArrays: ['items'] };
```
Использовать `encryptRecord(data, MY_SCHEMA)` при записи и `decryptRecord(row, MY_SCHEMA)` при чтении.
Ответ ручки записи (create/upsert/update) — через ту же функцию расшифровки, что GET,
а не пересборкой полей вручную: инцидент 2026-10-26 — POST дневника отдавал `schemaIds`
шифротекстом, раздел сайта падал. Сверку «ответ записи = GET» с настоящим ключом держит
`src/utils/encrypted-write-response.spec.ts` — новая модель с шифрованным полем
получает там случай или причину, почему строка наружу не уходит.
Не шифровать: `id`, `userId`, `createdAt`, `updatedAt`, типы-перечисления (modeId, schemaId, needId).

Механизм принуждения: `src/utils/encryption-coverage.spec.ts` — реестр решений
о шифровании для КАЖДОГО String/Json-поля каждой модели. Новое поле без записи
в реестре роняет jest в CI; `enc`-запись проверяется по исходнику сервиса,
`plain`-запись требует причину. Молча добавить plaintext-колонку со свободным
текстом невозможно (найдено аудитом 2026-07-20: черновики дневников, ответы
YSQ, заявки терапевтов, алиасы клиентов и email в magic-link токенах лежали
в открытом виде).

**3. Каскадное удаление в Prisma**
```prisma
user  User  @relation(fields: [userId], references: [id], onDelete: Cascade)
```

**4. После изменений схемы**
```bash
npx prisma generate
```
